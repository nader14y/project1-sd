# طرح دوره در ۱۲ جلسه (نسخه‌ی اجرایی — بازنگری‌شده)

سرفصل اصلی برای ۱۶ جلسه نوشته شده بود. این سند، نقشه‌ی فشرده‌ی ۱۲ جلسه‌ای است که
**اجرا می‌شود** — همه‌ی شماره‌ی جلسه‌ها در کیت‌های جلسات به این جدول ارجاع می‌دهند.

**بستر کلاس:** ویندوز (همه‌ی دانش‌آموزان) · پایتون + VS Code · git نصب‌شده در جلسه‌ی ۱

> 🔄 **بازنگری دوم:** جلسه‌ی ۲ کند پیش رفت و git نشد — علتش مفهوم نبود، **تسلط نداشتن
> بر ابزار** بود. پس **جلسه‌ی ۳ شد «ابزارها: VS Code + git»**.
>
> 🔄 **بازنگری سوم:** git و GitHub یک **جلسه‌ی کامل** گرفت (نه پراکنده در جلسات ۷ و ۸)،
> و **بعد از** جلسه‌ی موتور نشست: **۴ = موتور بازی، ۵ = git و GitHub**.
> دو دلیل: پاداش احساسی «اولین مسابقه‌ی دونفره» عقب نمی‌افتد، و وقتی عضو دوم
> `clone` می‌کند یک **پروژه‌ی واقعی دوفایلی** می‌گیرد، نه یک فایل.
> اسلات لازم از ادغام «ماژول‌بندیِ ساده‌شده» در جلسه‌ی موتور آمد (دو فایل، نه پوشه‌بندی).
> جلسات ۶ تا ۱۲ شماره‌شان دست‌نخورده ماند.
>
> 🛡 **قانون ۵ از جلسه‌ی ۵:** «هر جلسه با `push` تمام می‌شود» — بیمه‌ی از‌دست‌رفتن کار بچه‌ها.

## چه چیزی ادغام شد و چرا

**جلسه‌ی ۳ = ابزارها + git.** درس ابزار در سرفصل اصلی وجود نداشت، ولی تجربه‌ی جلسه‌ی ۲
نشان داد بدون آن هیچ برنامه‌ی زمانی‌ای جواب نمی‌دهد. ۲۵ دقیقه صرف دو گلوگاه واقعی
(فایل/پوشه/ذخیره، و ترمینال) به‌شکل **تمرین و مسابقه، نه سخنرانی**؛ بعد git با ۵۰ دقیقه
فرصت کامل. این ۲۵ دقیقه در جلسه‌ی ۴ به‌تنهایی برمی‌گردد.

**جلسه‌ی ۴ = موتور + ماژول‌بندیِ ساده‌شده.** ماژول‌بندی به‌جای ساختار پوشه‌ای
`game/ui/storage` با `__init__.py`، به **دو فایل** تقلیل پیدا کرد: `game.py` (موتور) و
`main.py` (نمایش). درس اصلی — «موتور print و input ندارد» — کامل می‌ماند؛ تشریفات
پکیج‌سازی که برای این سن بیشتر سربار است تا درس، حذف می‌شود.
ساختار کامل پوشه‌ای می‌شود **«مسیر پیشرفته»** برای تیم‌های سریع.

**جلسه‌ی ۹ = دیباگ/خطا/لاگ + README.** نوشتن README بیشترش تمرین خانه است؛ آنچه واقعاً
باید سر کلاس باشد «آزمون آتش» است (تیم مقابل فقط از روی README پروژه را اجرا می‌کند)
که ۲۵ دقیقه وقت می‌گیرد. docstring کامل → تمرین خانه.

**جلسه‌ی ۱۰ = انتشار + مانیتورینگ.** Sentry به یک **دموی ۱۰ تا ۱۵ دقیقه‌ای روی لپ‌تاپ مربی**
تقلیل پیدا کرد، نه راه‌اندازی روی لپ‌تاپ همه‌ی تیم‌ها. دیدنِ «خطا از کامپیوتر یک نفر دیگر
خودش آمد» ارزش دارد؛ ساختن حساب و راه‌اندازی روی ۸ لپ‌تاپ در کلاسی که کند پیش می‌رود، ندارد.
شکار باگ متقاطع طبیعی‌تر شد: تیم‌ها همان‌جا فایل اجرایی هم را می‌گیرند و می‌شکنند.

**جلسه‌ی ۱۱ = صیقل + ارائه + Release.** ضبط ویدیوی پلن B → تمرین خانه، نه وقت کلاس.

## چه چیزی حذف **نشد** (و نباید بشود)

- دموی زنده‌ی جلسه‌ی ۱ ✅
- جلسه‌ی کامل موتور بازی (جلسه‌ی ۴) — سنگین‌ترین و مهم‌ترین جلسه‌ی فنی.
  اگر طول کشید، ۲۰ دقیقه‌ی اول جلسه‌ی ۶ ذخیره‌ی اوست.
- جلسه‌ی کامل تست (جلسه‌ی ۷) با درس «زمان تزریقی»
- فایل اجرایی روی کامپیوتر بدون پایتون (جلسه‌ی ۱۰) — لحظه‌ی «واو» دوره
- روز دموی نهایی به‌صورت یک جلسه‌ی کامل (جلسه‌ی ۱۲)

## قوانین دوره (پوستر تجمعی — با شماره‌های جدید)

| جلسه | قانون |
|---|---|
| ۱ | هر جلسه با پروژه‌ی سالم تمام می‌شود. |
| ۲ | هر پروژه جعبه‌ابزار خودش را دارد (venv + requirements). |
| ۳ | همیشه پوشه را باز کن، نه فایل. · کاری که commit نشده، انجام نشده. |
| ۴ | موتور بازی print و input ندارد؛ زمان همیشه از بیرون تزریق می‌شود. کد جدید اول جواب می‌دهد: مغز است یا دهان؟ |
| ۵ | **هر جلسه با `push` تمام می‌شود.** |
| ۶ | فقط داده‌ای ذخیره می‌شود که از دست‌رفتنش فاجعه باشد. |
| ۷ | قبل از commit، pytest سبز. |
| ۸ | main همیشه سالم و قابل‌بازی است؛ کار روی branch، و ورود به main فقط با ریویو. |
| ۹ | except همیشه نوع‌دار و با واکنش؛ هر باگِ حل‌شده یک تستِ نگهبان می‌گیرد. |
| ۱۰ | خروجی ساخت، کد نیست. هیچ خطای دستِ کاربر بی‌خبر نمی‌ماند؛ در دوران فریز فقط fix. |
| ۱۱ | عوض‌کردن ظاهر نباید موتور را دست بزند. |

## نکات ویندوزی که کل دوره را تحت تأثیر می‌گذارد

| موضوع | تصمیم |
|---|---|
| ترمینال | **Command Prompt** به‌عنوان ترمینال پیش‌فرض VS Code — دو تله‌ی PowerShell (ExecutionPolicy و انکودینگ UTF-16) را یک‌جا حل می‌کند |
| مسیر پروژه | `C:\dev\quiz-battle` — **نه** Desktop و **نه** داخل OneDrive (sync پوشه‌ی venv فاجعه است) |
| نام مسیر | فقط انگلیسی، بدون فاصله |
| فعال‌سازی venv | `venv\Scripts\activate` |
| هویت git | `user.name` و `user.email` باید **قبل از جلسه‌ی ۳** روی همه‌ی لپ‌تاپ‌ها ست شده باشد، وگرنه اولین commit خطا می‌دهد |
| شاخه‌ی پیش‌فرض git | `init.defaultBranch = main` — تا با GitHub جلسه‌ی ۵ هماهنگ باشد |
| pager دستور `git log` | با `q` بسته می‌شود — تله‌ای که نصف کلاس در آن گیر می‌کند |
| فایل اجرایی جلسه‌ی ۱۰ | `.exe` ساخته‌شده روی ویندوز فقط روی ویندوز اجرا می‌شود — و کل کلاس ویندوزی است |
| اینترنت | جلسات ۵، ۸ و ۱۰ اینترنت لازم دارند. برای جلسه‌ی ۵ پلن B آفلاین («GitHub روی فلش») در کیتش هست |
| گرم‌کردن هر جلسه | **مسابقه‌ی راه‌اندازی** (۵ دقیقه) از جلسه‌ی ۳ به بعد، ابتدای هر جلسه — برگه‌اش در `session-03/handouts/speed-run.html` |
| فایل «نقطه‌ی شروع» | ابتدای هر جلسه به تیم‌های عقب‌مانده داده می‌شود تا شکاف تیم‌ها هر هفته دو برابر نشود |
| کپی‌پیست | برای کد **تکراری** آزاد؛ ممنوعیت فقط برای مفهوم **تازه** |
