# ۰ تا ۸ — بررسی تمرین + طرح مسئله

## دقیقه‌ی ۰ تا ۴ — تمرین خانه

**دو تیم** بازی‌شان را روی پرده اجرا کنند (نه بیشتر — وقت امروز طلاست).
دنبال سه چیز: ۵ سؤال دارد؟ شمارنده‌ی «سؤال ۲ از ۵» درست است؟ درصد آخر درست است؟

اگر کسی `total = 5` را دستی نوشته بود، **نقد نکنید** — یادداشت کنید، جلسه‌ی ۵ سراغ
«عدد جادویی» می‌رویم. اگر کسی `correct // total` نوشته و همیشه صفر می‌گیرد، **هدیه است**:
در ترمینال `3 // 5` را نشانش بدهید. سی ثانیه، درسی که یادش نمی‌رود.

## دقیقه‌ی ۴ تا ۸ — طرح مسئله (انگیزه قبل از ابزار)

بازی یکی از تیم‌ها روی پرده باشد:

> «بازی شما کار می‌کند — ولی شبیه سال ۱۹۸۵ است. دموی هفته‌ی پیش من رنگ داشت،
> کادر داشت، جدول امتیاز داشت. آن جادو یک **کتابخانه** است به اسم `rich`.»

مکث. بعد:

> «الان نصبش می‌کنیم؟ نه. اول باید یک عادت حرفه‌ای بسازیم — وگرنه همین کتابخانه
> هفته‌ی دیگر برایمان دردسر می‌شود.»

**سناریوی درد (بازی‌اش کنید، نگویید):**

> «فرض کنید `rich` را نصب کردید و بازی‌تان رنگی شد. فایل `game.py` را برای هم‌تیمی‌ات
> می‌فرستی. روی لپ‌تاپ او... **اجرا نمی‌شود.** چرا؟»
> — «چون او `rich` ندارد!»
> «راه‌حل چیست؟ زنگ بزنیم بگوییم چه نصب کند؟ و اگر ۱۰ کتابخانه بود؟ و اگر شش ماه بعد
> خودت روی لپ‌تاپ جدید بخواهی اجرا کنی، یادت است چه نصب کرده بودی؟»

بی‌جواب می‌ماند تا دقیقه‌ی ۲۴. **همین درد، سوخت نیمه‌ی اول جلسه است.**

این را باید در **۵ دقیقه‌ی قبل از شروع کلاس** انجام داده باشید (چک‌لیست آماده‌سازی).
اگر نشده، همین‌جا ۲ دقیقه وقت بگذارید: همه پروژه‌شان در `C:\dev\quiz-battle` باشد —


`deactivate` را فقط نشان بدهید و دوباره فعال کنید.

**⏸ نقطه‌ی توقف ۱:** همه `(venv)` را می‌بینند؟ هیچ‌کس نباید عقب بماند.

# ۲۴ تا ۳۳ — requirements.txt

```bat
pip install rich
```

بپرسید: **«چند تا چیز نصب شد؟»** — جواب: `rich` + سه بسته‌ی دیگر.
> «کتابخانه‌ها هم به کتابخانه‌های دیگر وابسته‌اند. برای همین دستی یادداشت‌کردن جواب نمی‌دهد.»

```bat
pip freeze > requirements.txt
```

فایل را در VS Code باز کنند: چهار خط با نسخه‌ی دقیق.

**⚠️ چک انکودینگ (۲۰ ثانیه):** گوشه‌ی **پایین-راست** VS Code باید بنویسد `UTF-8`.
اگر `UTF-16 LE` بود → ترمینالشان PowerShell بوده. فایل را پاک کنند، ترمینال را
Command Prompt کنند، دوباره بزنند.

> «چرا مهم است؟ چون `pip` نمی‌تواند بخواندش — و شما یک ساعت دنبال باگی می‌گردید که در کد شما نیست.»

**چرا `==`؟**
> «شش ماه بعد `rich` عوض می‌شود و کد شما نمی‌چرخد. این علامت تضمین می‌کند همان نسخه نصب شود.»

و روی تخته بنویسید (دقیقه‌ی ۴۷ لازمش دارند):

```bat
pip install -r requirements.txt
```

> «جواب همان سؤال دقیقه‌ی ۵: دیگر لازم نیست به کسی زنگ بزنی.»

# ۳۳ تا ۴۷ — اولین رنگ‌ها با rich

## دقیقه‌ی ۳۳ تا ۳۸ — سه ابزار، نه بیشتر

فایل جدا `rich_test.py` (`live-code/stage1_rich_hello.py`):

```python
from rich.console import Console

console = Console()

console.print("✅ درست!", style="bold green")
console.print("❌ غلط! جواب درست: C", style="bold red")
console.print("[bold cyan]سؤال ۲ از ۵[/bold cyan] — بزرگ‌ترین سیاره؟")
```

| | چیست |
|---|---|
| `Console()` | یک‌بار ساخته می‌شود؛ از این به بعد `console.print` به‌جای `print` |
| `style="bold green"` | رنگ **کل** خط |
| `[bold cyan]...[/bold cyan]` | رنگ **بخشی** از خط — مثل تگ، باید بسته شود |

**🔒 مرز امروز:** «`rich` کادر و جدول و نوار پیشرفت هم دارد. **امروز نه.** عمقش مال جلسه‌ی ۱۱.»

# ۵۷ تا ۸۵ — git: راه برگشت

## دقیقه‌ی ۵۷ تا ۶۲ — فاجعه‌ی طراحی‌شده 💣

**این ۵ دقیقه، قلب بلوک git است. کوتاهش نکنید.**

همه سر لپ‌تاپ خودشان برگشته‌اند. با لحن کاملاً عادی، مثل یک تسک معمولی:

> «یک تغییر کوچک: سیستم امتیاز را بازنویسی کنید. به‌جای ۱۰، هر سؤال **۲۰ امتیاز**
> بدهد، و جواب غلط **۵ امتیاز کم** کند. سه دقیقه وقت دارید.»

بگذارید واقعاً انجامش بدهند. اجرا کنند. کار می‌کند. حالا:

> «عالی. راستش... **مدیرِ محصول (یعنی من) نظرش عوض شد.** برگردید دقیقاً به نسخه‌ی قبل.
> دقیقاً. همان‌طور که بود.»

بگذارید Ctrl+Z بزنند. کار می‌کند — **تا وقتی که**:
- یکی فایل را بسته و باز کرده باشد → تاریخچه‌ی Ctrl+Z رفته
- یکی چند جای مختلف را دست زده باشد → یادش نیست کجاها
- یکی زیادی Ctrl+Z زده باشد → حالا رنگ‌هایش هم رفته!

سه چهار نفر حتماً گیر می‌کنند. **همان‌ها را بلند بپرسید:** «الان دقیقاً همان نسخه‌ی
قبل را داری؟ مطمئنی؟»

بعد جمله‌ی کلیدی:

> «برنامه‌نویس واقعی از خراب‌کردن نمی‌ترسد، چون **همیشه راه برگشت دارد.**
> امروز آن راه را می‌سازیم.»

## دقیقه‌ی ۶۲ تا ۷۲ — اولین commit

**تشبیه (روی تخته):**
> «git دکمه‌ی **save** بازی است. commit یعنی save. هر جا save کردی، هر وقت خواستی برمی‌گردی.»

**سه ناحیه، بدون اصطلاح‌بازی:**

```
پوشه‌ی کار  ──add──▶  سبد خرید  ──commit──▶  آلبوم عکس
(working)            (staging)              (history)
```

> «هر چیزی که می‌سازی توی پوشه‌ی کار است. آنچه می‌خواهی این دفعه ثبت شود را می‌گذاری
> در سبد. بعد از سبد یک عکس می‌گیری و می‌چسبانی در آلبوم. آلبوم هیچ‌وقت پاک نمی‌شود.»

```bat
git init
git status
```

`git status` همه‌چیز را **قرمز** نشان می‌دهد = «ناشناخته، هنوز در سبد نیست».

**⛔ اینجا توقف کنید — قبل از `git add .`**

بگذارید خوب به خروجی `git status` نگاه کنند. پوشه‌ی `venv` هم آنجاست، با کلی فایل.

> **«پوشه‌ی venv باید در آلبوم باشد؟ چرا نه؟»**

بگذارید خودشان جواب بدهند — جواب را **۲۵ دقیقه پیش** خودشان گفتند:
«چون سنگین است و از روی requirements دوباره ساخته می‌شود.»

این لحظه را بزرگ کنید: **«همان قانونی که در آزمون تعویض کشف کردید، حالا می‌شود یک فایل.»**

## دقیقه‌ی ۷۲ تا ۷۸ — .gitignore

فایل `.gitignore` بسازند (بدون پسوند، با نقطه‌ی اول — در VS Code راحت است):

```
venv/
__pycache__/
```

> «هر خط یعنی: git، این را اصلاً نبین.»

`git status` دوباره → تمیز شد. حالا:

```bat
git add .
git status
git commit -m "Add colored quiz with 5 questions"
git log --oneline
```

**🚨 تله‌ی ویندوزی — حتماً از قبل بگویید:** خروجی `git log` در یک صفحه‌ی مخصوص باز
می‌شود که با فلش بالا/پایین حرکت می‌کند و **با کلید `q` بسته می‌شود**. اگر نگویید،
نصف کلاس گیر می‌کند و فکر می‌کند ترمینال هنگ کرده.

**⚠️ پیام `LF will be replaced by CRLF`:** روی ویندوز عادی است، خطا نیست.
یک جمله: «ویندوز و بقیه‌ی دنیا سر پایان خط توافق ندارند؛ git خودش ترجمه می‌کند.»

هر کس hash کوتاه commit خودش را می‌بیند: **«شماره‌ی این save.»**

## دقیقه‌ی ۷۸ تا ۸۵ — سفر در زمان 🎉 (نقطه‌ی اوج جلسه)

حالا انتقام فاجعه‌ی دقیقه‌ی ۵۷:

> «حالا بازی‌تان را **عمداً خراب کنید**. هرچه دلتان می‌خواهد. چند خط پاک کنید،
> وسطش چرت‌وپرت بنویسید. ذخیره کنید. اجرا کنید — باید خراب باشد.»

بگذارید واقعاً خرابش کنند (بچه‌ها عاشق این قسمت‌اند). بعد:

```bat
git status

```

فایل را باز کنند: **سالم برگشته.** 🎉

بگذارید کلاس واکنش نشان بدهد. بعد:

> «همان کاری که ۲۵ دقیقه پیش با Ctrl+Z نتوانستید بکنید، حالا با یک دستور شد.
> و مهم‌تر: **مهم نیست فایل را بسته باشی، کامپیوتر را خاموش کرده باشی، یا یک هفته
> گذشته باشد.** آلبوم یادش می‌ماند.»

**قرارداد پیام commit** (۲ دقیقه، روی تخته):

- ✅ `Add start menu` · ✅ `Fix score not resetting`
- ❌ `تغییرات` · ❌ `final2` · ❌ `asdfgh`

> «فعل امری + چه چیزی + کوتاه. پیام commit را برای **خودتِ سه ماه بعد** می‌نویسی.»

**⚠️ نکته‌ی مربی — این را به بچه‌ها یاد ندهید:** `git reset --hard`.
خطرناک‌ترین ابزار git را دست تازه‌کار ندهید. اگر کسی از اینترنت پیدایش کرد و پرسید،
بگویید «هست، ولی دو جلسه‌ی دیگر.»

# ۸۵ تا ۹۰ — جمع‌بندی و تمرین خانه

سه سؤال، و **جواب را از خودشان بگیرید**:

1. `venv` چه دردی را دوا کرد؟ → «هر پروژه ابزار خودش را دارد.»
2. `requirements.txt` چه دردی را دوا کرد؟ → «هر کسی با یک دستور همه‌چیز را نصب می‌کند.»
3. `git` چه دردی را دوا کرد؟ → «همیشه راه برگشت دارم.»

**دو قانون جدید** روی پوستر:

> ## قانون ۲: هر پروژه جعبه‌ابزار خودش را دارد.
> ## قانون ۳: کاری که commit نشده، انجام نشده.

قانون ۳ را جدی اعلام کنید: **«از این پس هر جلسه حداقل ۲ commit معنادار. اگر commit

# 🪜 نردبان حذف (اگر عقب افتادید)

این جلسه متراکم است. به این ترتیب حذف کنید — از بالا:

1. ~~`deactivate` و `where python`~~ (۲ دقیقه)
2. ~~بازی‌کردن با رنگ‌های مختلف در `rich_test.py`~~ — مستقیم بروید سراغ بازی (۳ دقیقه)
3. ~~رنگی‌کردن پیام پایانی و امتیاز~~ → تمرین خانه (۳ دقیقه)
4. ~~آزمون تعویض برای همه~~ → فقط **دو تیم جلوی کلاس** انجامش بدهند (۶ دقیقه)
5. ~~قرارداد پیام commit~~ → روی برگه‌ی تمرین خانه هست، ارجاع بدهید (۲ دقیقه)

**سه چیزی که هرگز حذف نمی‌شوند:**
- **فاجعه‌ی طراحی‌شده** — بدون درد، git فقط یک مشت دستور عجیب است
- **`git restore`** — لحظه‌ی «واو» بلوک git
- **`.gitignore` و سؤال «venv باید در آلبوم باشد؟»** — پل بین دو نیمه‌ی جلسه

اگر دیدید حتی با نردبان هم نمی‌رسید، **بلوک git را ناقص رها نکنید**: بهتر است
آزمون تعویض کاملاً حذف شود (و به ابتدای جلسه‌ی ۳ منتقل شود) تا git ۲۸ دقیقه‌ی کاملش را داشته باشد.

# مشکلات ویندوزی و راه‌حل آماده

## venv و pip

| پیام / نشانه | علت | راه‌حل |
|---|---|---|
| `python` زدم، Microsoft Store باز شد | PATH ندارد | `py -m venv venv` |
| `'python' is not recognized` | PATH ندارد | مثل بالا؛ یا نصب مجدد با تیک **Add to PATH** |
| `cannot be loaded because running scripts is disabled` | PowerShell + ExecutionPolicy | ترمینال را Command Prompt کنید؛ یا `Set-ExecutionPolicy -Scope CurrentUser RemoteSigned` |
| در PowerShell activate کاری نکرد | نام دستور فرق دارد | `.\venv\Scripts\Activate.ps1` |
| `(venv)` نیامد، خطا هم نداد | ترمینال قبل از ساخت venv باز بوده | ترمینال را ببندید و باز کنید |
| `ModuleNotFoundError: No module named 'rich'` | venv فعال نیست (۹۵٪ موارد) | `venv\Scripts\activate` |
| `requirements.txt` به‌هم‌ریخته | PowerShell با `>` فایل را UTF-16 می‌سازد | Command Prompt؛ یا `pip freeze \| Out-File -Encoding utf8 requirements.txt` |
| `Access is denied` روی venv | OneDrive قفل کرده | پروژه را به `C:\dev` منتقل کنید |

## git

| پیام / نشانه | علت | راه‌حل |
|---|---|---|
| `Please tell me who you are` هنگام commit | هویت git ست نشده | `git config --global user.name "Ali"` و `git config --global user.email "ali@example.com"` — **باید قبل از کلاس انجام شده باشد** |
| ترمینال بعد از `git log` هنگ کرده! | صفحه‌ی pager باز است | کلید **`q`** |
| `warning: LF will be replaced by CRLF` | تفاوت پایان خط ویندوز | عادی است، خطا نیست |
| `git` شناخته نمی‌شود | git نصب نیست یا PATH ندارد | VS Code را ری‌استارت کنید؛ اگر نشد git را دوباره نصب کنید |
| `git init` هشدار master/main داد | نام شاخه‌ی پیش‌فرض ست نشده | `git config --global init.defaultBranch main` — در چک‌لیست آماده‌سازی |
| `.gitignore` ساختم ولی venv هنوز دیده می‌شود | فایل به اسم `.gitignore.txt` ذخیره شده | در VS Code بسازید، نه Notepad؛ اسم باید دقیقاً `.gitignore` باشد |
| هزاران فایل در `git status` | `.gitignore` قبل از `git add` ساخته نشده | `.gitignore` را بسازید، بعد `git add .` |
| `nothing to commit, working tree clean` | فایل ذخیره نشده (Ctrl+S) | ذخیره کنند و دوباره |
