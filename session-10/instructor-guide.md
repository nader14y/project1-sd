# جلسه‌ی ۱۰ — کار تیمی با git، و بازی‌ای که نمی‌میرد
## راهنمای دقیقه‌به‌دقیقه‌ی مربی · کلاس ویندوزی

**هدف جلسه:** مفاهیم باقی‌مانده‌ی git (`branch`، PR، کد ریویو، conflict، `revert`) —
و **سوختشان، فیکس‌های واقعیِ امروز است**: بازی دیگر با نام تکراری یا فایلِ خراب نمی‌میرد.

> ⭐ **تصمیم مرکزی این جلسه:** branch و conflict را با یک مثالِ ساختگی یاد نمی‌دهیم.
> دو عضو هر تیم **دو فیکسِ واقعی** را هم‌زمان روی `game.py` می‌زنند — و conflict
> خودش، طبیعی، اتفاق می‌افتد. تستش کرده‌ام: **یک ناحیه‌ی conflict، هفت خط،
> و هر دو طرف درست‌اند.** بهتر از این برای آموزش پیدا نمی‌شود.

## ⚠️ چهار چیزی که قبل از شروع بدانید

**۱. این جلسه از نظر زمانی هیچ چربی ندارد.** دو بلوکِ بزرگ (git تیمی + مدیریت خطا)
در یک جلسه جا شده‌اند، و تنها دلیلِ ممکن‌بودنش این است که **دومی سوختِ اولی است**.
سه چیز عمداً به تمرین خانه رفته‌اند: تست‌های نگهبان، تورِ آخر، و README.
نردبان حذف را از قبل بخوانید.

**۲. اینترنت امروز لازم است** (PR روی GitHub). اگر شبکه خراب شد، برنامه‌ی B در
چک‌لیست هست: همه‌ی مراحل جز خودِ صفحه‌ی PR، لوکال هم کار می‌کنند.

**۳. مرورِ ۱۰ دقیقه‌ای تست‌ها را طوری تمام کنید که به امروز وصل شود.** آخرین
جمله‌تان این باشد — و بعد **ساکت شوید**:

> «۲۵ تست داریم و همه سبزند. **پس بازی ما سالم است، درست است؟**»

**۴. تقسیم کار را از قبل روی کاغذ بنویسید.** وقتِ کلاس برای «کی چه کار کند؟»
هدر نرود. جدولش در چک‌لیست آماده است.

# ۱۸ تا ۲۸ — 🌿 branch

## دقیقه‌ی ۱۸ تا ۲۲ — اول درد

> «تا حالا هر دو نفرِ تیم، نوبتی روی `main` کار کردید. حالا فرض کنید هر دو
> **هم‌زمان** `game.py` را عوض کنید و هر دو `push` کنید. چه می‌شود؟»

بگذارید حدس بزنند. بعد:

> «نفر دوم اصلاً نمی‌تواند push کند — git می‌گوید "عقبی، اول pull کن".
> و بدتر: اگر وسطِ کارِ نیمه‌کاره‌ی تو push کنم، **بازیِ تو هم می‌شکند.**»

> ## «`main` همیشه باید سالم و قابل‌بازی باشد. پس کارِ نیمه‌کاره، جای دیگری انجام می‌شود.»

## دقیقه‌ی ۲۲ تا ۲۵ — مدل ذهنی، روی تخته

این شکل را بکشید — همان است که آخر جلسه با `git log --graph` واقعاً می‌بینند:

```
main      ───●────────────────●─── merge ──●───
               \             /
fix/names       ●───●───────/
```

> «branch یعنی یک **خطِ زمانیِ موازی**. کار می‌کنی، خراب می‌کنی، درست می‌کنی —
> و `main` دست‌نخورده می‌ماند. وقتی کارت تمام و سالم شد، **برش می‌گردانی** به main.»

```bat
git switch -c fix/duplicate-names
```

> «`-c` یعنی *create*. اسم branch را از روی **کاری که می‌کند** می‌گذاریم، نه اسم خودمان.»

## دقیقه‌ی ۲۵ تا ۲۸ — تقسیم کار

روی تخته، و **از قبل تصمیم گرفته باشید کی کدام است**:

| نفر | branch | فیکس |
|---|---|---|
| عضو ۱ | `fix/duplicate-names` | نام تکراری → دوباره بپرس |
| عضو ۲ | `fix/question-bank` | بانک سؤالِ نبود و خراب → پیام روشن |

⚠️ **و این یک خط را به هر دو نفر بگویید** — بذرِ conflict است و عمدی:

> «**هر دو نفر** باید بلوکِ لاگ را بالای `game.py` اضافه کنید، چون هر دوتان
> برای فیکسِ خودتان به آن احتیاج دارید.»

# ۲۸ تا ۴۸ — ⌨️ هر نفر، فیکسِ خودش

**بلوکِ مشترک (هر دو نفر، بالای `game.py`):**

```python
import logging

logging.basicConfig(
    level=logging.INFO,
    format="%(asctime)s [%(levelname)s] %(message)s",
    handlers=[logging.FileHandler("game.log", encoding="utf-8")],
)
```

> «لاگ، دفترچه‌ای است که برنامه برای **خودش** می‌نویسد، نه برای کاربر.
> `print` را کاربر می‌بیند، `log` را تو.» و `game.log` → `.gitignore`.

## ⭐ عضو ۱ — نام تکراری (و درسِ معماریِ امروز)

**قبل از کد، این سؤال را از کلِ کلاس بپرسید:** «قاعده‌ی نام تکراری را کجا چک کنیم؟»

تقریباً همیشه اولین جواب این است: «یک `if` در `game.py`».
**بنویسیدش روی تخته و بعد خرابش کنید:**

> «اگر این را بنویسیم، قاعده **دو جا** نوشته شده: یک‌بار در موتور، یک‌بار اینجا.
> فردا قاعده عوض شود، **کدام را عوض می‌کنی؟ یادت می‌ماند دوتاست؟**»

> ## «قاعده یک جا زندگی می‌کند: در موتور. دهان فقط فریادش را می‌گیرد و دوباره می‌پرسد.»

```python
def ask_names(questions):
    while True:
        player1_name = input("نام بازیکن اول: ").strip() or "بازیکن 1"
        player2_name = input("نام بازیکن دوم: ").strip() or "بازیکن 2"

        try:
            return Match(player1_name, player2_name, questions)
        except ValueError as error:
            logging.warning("ساختن مسابقه نشد: %s", error)
            console.print(f"⛔ {error}", style="bold red")
            console.print("دوباره امتحان کن.\n", style="yellow")
```

و در `play`: `match = play_match(ask_names(bank.pick(ROUNDS)))`
*(و `play_match` به‌جای سه ورودی، یک `match` آماده می‌گیرد.)*

🇮🇷 **وقتی امتحانش کردند، یکی می‌گوید «پیام انگلیسی است!»** — بهترین لحظه:
> «درست. و چون فقط **یک جا** نوشته شده، فقط یک جا عوضش می‌کنیم.»
یک رشته در `engine.py` → همه‌جا فارسی شد. **سودِ نقدیِ تصمیمِ پنج دقیقه پیش.**

## عضو ۲ — بانک سؤال (و درسِ «دو تصمیم»)

در `storage.py`:

```python
        if not Path(path).exists():
            raise FileNotFoundError(f"فایل بانک سؤال پیدا نشد: {path}")

        try:
            with open(path, "r", encoding="utf-8") as f:
                data = json.load(f)
        except json.JSONDecodeError as error:
            raise ValueError(
                f"فایل بانک سؤال خراب است (خط {error.lineno}): {error.msg}"
            ) from error
```

⭐ **`error.lineno` مهم‌ترین تکه‌ی این فیکس است:** «خطای خام می‌گفت یک جایی خراب است.
ما **شماره‌ی خط** را اضافه می‌کنیم. فرقِ پیامِ بی‌فایده و پیامِ قابل‌استفاده همین است.»

و در `game.py` → `main()`:

```python
    try:
        bank = QuestionBank()
    except FileNotFoundError as error:
        console.print(f"⛔ {error}", style="bold red")
        console.print("فایل questions.json باید کنار game.py باشد.", style="yellow")
        logging.error("بانک سؤال پیدا نشد: %s", error)
        return
    except ValueError as error:
        console.print(f"⛔ {error}", style="bold red")
        console.print("فایل را در VS Code باز کن و Shift+Alt+F بزن.", style="yellow")
        logging.error("بانک سؤال خراب است: %s", error)
        return
```

> «دو `except` جدا، چون **دو واکنشِ جدا**. هر دو می‌گویند چه شد، ولی هر کدام
> می‌گوید **حالا چه کار کن**. پیامی که این را نگوید، نصفه است.»

## ⚖️ دقیقه‌ی ۴۴ — سه دقیقه که از همه‌ی امروز بیشتر «مهندسی» دارد

وقتی عضو ۲ دارد کار می‌کند، کلِ کلاس را نگه دارید و بپرسید:

> «اگر `leaderboard.json` خراب باشد چه؟ آن هم باید بازی را ببندیم؟»

جواب **نه** است، و معیارش یک سؤال:

> ## «بدون این داده می‌شود بازی کرد؟»

| فایل | بدونش می‌شود بازی کرد؟ | پس |
|---|---|---|
| `questions.json` | ❌ نه | فریاد بزن و تمیز ببند |
| `leaderboard.json` | ✅ بله (حیف است، ولی می‌شود) | از نو شروع کن و **ادامه بده** |

```python
            try:
                with open(self._path, encoding="utf-8") as f:
                    self._data = json.load(f)
            except (json.JSONDecodeError, OSError):
                self._data = {}          # رده‌بندیِ خراب، دلیلِ مُردنِ بازی نیست
```

> «دو فایل، دو تصمیم. **مدیریت خطا یعنی تصمیم‌گیری، نه چسباندنِ `try` به همه‌جا.**»

# ۴۸ تا ۶۰ — 🔀 PR اول و کد ریویو

## دقیقه‌ی ۴۸ تا ۵۲ — PR یعنی چه

روی GitHub، بالای صفحه دکمه‌ی **Compare & pull request** ظاهر شده.

> «PR یعنی: *من کارم تمام شد. قبل از اینکه برود در `main`، یکی نگاهش کند.*
> **دکمه‌ی merge را خودت نمی‌زنی.** اول هم‌تیمی‌ات نگاه می‌کند.»

عنوان PR را جدی بگیرید:
> «عنوان، **کاری** که کردی را می‌گوید؛ توضیح، **چرایش** را.»

## ⭐ دقیقه‌ی ۵۲ تا ۵۷ — کد ریویو، با قاعده

**هر دو نفر PR همدیگر را باز می‌کنند، تب Files changed.** و این قاعده روی تخته:

> ## هر ریویو **حداقل یک کامنت** دارد. «خوبه» کامنت نیست.

سه نوع کامنتِ مجاز — یکی‌شان را انتخاب کن:

| نوع | مثال |
|---|---|
| ❓ **سؤال** | «اگر اسم خالی بگذارد چه می‌شود؟» |
| 💡 **پیشنهاد** | «این پیام را فارسی کنیم؟» |
| 👏 **تحسینِ مشخص** | «اینکه `error` را دوباره ننوشتی و همان موتور را نشان دادی، عالیه» |

> «ریویو یعنی **دو جفت چشم**، نه امتحان‌گرفتن. و تحسین هم ریویو است —
> ولی باید بگوید **چه چیزی** خوب بود.»

## دقیقه‌ی ۵۷ تا ۶۰ — merge

نویسنده کامنت را جواب می‌دهد، بعد **ریویوکننده** دکمه‌ی Merge را می‌زند. 🎉

```bat
git switch main
git pull
```

> «`main` حالا فیکسِ نفر اول را دارد. و `main` **سالم** است.»

# ۶۰ تا ۷۵ — 💥 conflict واقعی

## دقیقه‌ی ۶۰ تا ۶۴ — بگذارید اتفاق بیفتد

حالا نفر دوم PR خودش را می‌دهد. GitHub می‌گوید:

```
This branch has conflicts that must be resolved
```

**پیش‌بینی‌اش کنید و لذت ببرید:**

> «چرا؟ چون **هر دوتان** آن بلوکِ لاگ را بالای `game.py` اضافه کردید.
> git دو نسخه‌ی متفاوت از **همان خط‌ها** دارد و **نمی‌داند کدام درست است**.»

> ## «git هیچ‌وقت نمی‌داند کدام درست است. این یک **تصمیمِ انسانی** است.»

## دقیقه‌ی ۶۴ تا ۷۲ — حل، روی لپ‌تاپِ نفر دوم

```bat
git switch fix/question-bank
git pull origin main
```

VS Code فایل را با نشانه‌ها باز می‌کند:

```
<<<<<<< HEAD
    format="%(asctime)s [%(levelname)s] %(message)s",
    handlers=[logging.FileHandler("game.log", encoding="utf-8")],
=======
    filename="game.log",
    encoding="utf-8",
    format="%(asctime)s [%(levelname)s] %(message)s",
>>>>>>> fix/question-bank
```

**سه خطِ نشانه را با هم بخوانید:**

| نشانه | یعنی |
|---|---|
| `<<<<<<< HEAD` | از اینجا، **مالِ main** (کارِ نفر اول) |
| `=======` | مرز |
| `>>>>>>> fix/...` | تا اینجا، **مالِ من** |

VS Code چهار دکمه می‌دهد: `Accept Current` · `Accept Incoming` · `Accept Both` · `Compare`.

**⭐ و اینجا بایستید — مهم‌ترین نکته‌ی این بلوک:**

> «نگاه کنید: **هر دو نسخه درست‌اند.** هر دو لاگ را در `game.log` می‌نویسند.
> هیچ‌کس اشتباه نکرده. پس جوابِ درست، "مالِ من" یا "مالِ او" نیست —
> **یکی‌شان را انتخاب می‌کنیم و آن یکی را پاک.**»

> ⚠️ «و `Accept Both` اینجا **غلط** است — دو تا `basicConfig` می‌شود.»

بعد: نشانه‌ها پاک، فایل سالم، و:

```bat
pytest
git add game.py
git commit -m "Merge main into question bank fix"
git push
```

> «قانون ۷ یادتان هست؟ **اول pytest، بعد commit.** مخصوصاً بعد از conflict —
> چون موقع حل‌کردن، خیلی راحت یک خط اضافه پاک می‌شود.»

## دقیقه‌ی ۷۲ تا ۷۵ — merge دوم

PR حالا سبز است. ریویو، یک کامنت، merge. 🎉

```bat
git switch main
git pull
python game.py
```

**همه با هم امتحان کنند:** نام تکراری، فایلِ قایم‌شده، ویرگولِ اضافه.
**هر سه قتلِ ابتدای جلسه، حالا پیام آدمیزاد می‌دهند.** 📸 عکس بگیرید.

## ⭐ دقیقه‌ی ۷۸ تا ۸۵ — `revert`: اشتباهی که پاک نمی‌شود، برگردانده می‌شود

**یک تغییرِ عمداً بد بزنید و commit کنید** (مثلاً یک خط چاپِ مزاحم)، push کنید،
و بعد وانمود کنید فاجعه شده:

```bat
git log --oneline
git revert <هشِ آن commit>
```

> «ببینید چه شد: git آن commit را **پاک نکرد**. یک commitِ **تازه** ساخت که
> دقیقاً عکسِ آن را انجام می‌دهد.»

بپرسید: **«چرا پاکش نکرد؟ ساده‌تر نبود؟»**

> «چون این commit **روی GitHub رفته** و شاید هم‌تیمی‌ات pull کرده باشد.
> تاریخچه‌ای که دیگران دارند را نمی‌شود پاک کرد — ولی می‌شود **تصحیحش کرد**.
> مثل دفتری که با خودکار نوشته شده: پاک نمی‌کنی، یک خط جدید می‌نویسی.»

🌱 و یک بذر: «راه‌های دیگری هم برای برگشتن هست — مثلاً برگرداندنِ **یک فایل** به
نسخه‌ی یک commitِ قدیمی. روی کارت نوشته شده، در خانه امتحان کنید.»

# 🪜 نردبان حذف

این جلسه چربی ندارد. به ترتیب:

1. ~~`git show`~~ → روی کارت هست (۲ دقیقه)
2. ~~`revert`~~ → تمرین خانه، با دستورش روی کارت (۷ دقیقه)
3. ~~بحثِ «دو تصمیم برای دو فایل» (دقیقه‌ی ۴۴)~~ → فیکسِ `leaderboard` را خودتان
   بدهید و **فقط جدولش** را بگویید (۳ دقیقه)
4. ~~کامنتِ اجباری در ریویو~~ → فقط PR و merge، بدون ریویو — **ولی این یعنی
   نصفِ درسِ PR رفت** (۵ دقیقه)
5. ~~فیکسِ بانک سؤال برای همه~~ → عضو ۲ تنها بزند و بقیه تماشا (۸ دقیقه)

**چهار چیزی که هرگز حذف نمی‌شوند:**
- **دادگاهِ خرابی.** بدون دیدنِ سه قتل، کلِ جلسه بی‌دلیل است.
- **تقسیم کار روی دو branch.** اگر هر دو روی `main` کار کنند، conflict اتفاق نمی‌افتد
  و درسِ اصلی از بین می‌رود.
- **conflict و حلش.** قلبِ جلسه است.
- **«قاعده یک جا زندگی می‌کند».** اگر `if` را در `game.py` بگذارند، درسِ معماریِ
  شش جلسه را امروز خراب کرده‌اید.

**اگر عقب افتادید:** `revert` و `show` را به تمرین خانه ببرید — ولی
**conflict را به جلسه‌ی بعد نیندازید**، چون جلسه‌ی ۱۱ `.exe` است و جا ندارد.

# سؤال‌هایی که بچه‌ها می‌پرسند

**«چرا خودم merge نکنم؟ کدِ خودم است!»**
> «چون دو جفت چشم بهتر از یکی است. و چون `main` مالِ **تیم** است، نه تو.
> در شرکت‌های واقعی هم همین است — حتی برای کسی که ۲۰ سال تجربه دارد.»

**«conflict یعنی خراب کردم؟»**
> «نه! conflict یعنی **دو نفر هم‌زمان کار کردند** — یعنی تیم دارد کار می‌کند.
> اتفاقاً اگر هیچ‌وقت conflict نگیرید، یعنی هم‌زمان کار نمی‌کنید.»

**«چرا git خودش conflict را حل نمی‌کند؟»**
> «چون **نمی‌داند کدام درست است.** امروز دیدید: هر دو نسخه کار می‌کردند.
> git حدس نمی‌زند — این کارِ آدم است.»

**«می‌شود branch را بعد از merge پاک کرد؟»**
> «بله و باید. GitHub خودش دکمه‌اش را می‌دهد: `Delete branch`. کارش تمام شده،
> و تاریخچه‌اش در `main` است.»

**«`revert` با `restore` چه فرقی دارد؟»**
> «`restore` فایلِ **ذخیره‌نشده** را برمی‌گرداند. `revert` یک **commitِ انجام‌شده** را
> خنثی می‌کند — آن هم با ساختنِ یک commitِ تازه، نه با پاک‌کردن.»

**«پس هر جای برنامه باید `try` بگذاریم؟»**
> «نه! `try` جایی می‌گذاریم که **می‌دانیم** چه خراب می‌شود و **می‌دانیم آن‌وقت چه کنیم**.
> اگر جوابی برای "حالا چه کار کنم؟" نداری، `try` نگذار.»
