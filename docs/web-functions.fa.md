# مستندات توابع web.py

فایل [web.py](../web.py) رابط HTTP بازی کوییز را با Flask تعریف می‌کند. این فایل ساخت برنامه، نشست مرورگر، مسیرهای API، پاسخ‌های خطا و اجرای سرور را بر عهده دارد. مدیریت نوبت‌ها و زمان در [web_game.py](../web_game.py) و قوانین و محاسبهٔ امتیاز در [engine.py](../engine.py) انجام می‌شوند.

تمام توابع تعریف‌شده در این فایل، به‌جز `create_app`، داخل همان تابع قرار دارند. آن‌ها به برنامهٔ ساخته‌شده، متغیر `store` و `logger` دسترسی دارند و Flask آن‌ها را هنگام دریافت درخواست صدا می‌زند. برای استفادهٔ معمول، نیازی به فراخوانی مستقیم این توابع داخلی نیست.

## مسیر اجرای یک درخواست

```text
مرورگر
  → سرور Waitress
  → prepare_request
  → تابع مسیر، مانند answer
  → GameStore و موتور بازی
  → پاسخ عادی یا یکی از توابع مدیریت خطا
  → complete_request
  → مرورگر
```

`prepare_request` پیش از اجرای تابع مسیر و `complete_request` پس از تولید پاسخ اجرا می‌شوند. اگر خطایی رخ دهد، تابع مدیریت خطای مناسب پاسخ را می‌سازد و سپس `complete_request` هدرها و لاگ درخواست را اضافه می‌کند.

## ساخت برنامه با create_app

```python
def create_app(config=None):
```

یک نمونهٔ `Flask` می‌سازد، تنظیمات را اعمال می‌کند، لاگ وب را راه‌اندازی می‌کند و یک `GameStore` برای بازی‌های همان برنامه ایجاد می‌کند. سپس توابع پردازش درخواست، مدیریت خطا و مسیرها را ثبت می‌کند و در پایان نمونهٔ `app` را برمی‌گرداند. این تابع به‌تنهایی سرور شبکه را اجرا نمی‌کند.

| مورد | توضیح |
|---|---|
| ورودی `config` | دیکشنری اختیاری تنظیمات؛ مقدار پیش‌فرض `None` است |
| خروجی | نمونهٔ `flask.Flask` با مسیرهای ثبت‌شده |
| دسترسی به مخزن بازی | `app.extensions["quiz_store"]` |
| وابستگی‌ها | `AppLog.setup_web`، `GameStore` و ثابت `RULES` |

مقادیر `config` پس از تنظیمات پیش‌فرض اعمال می‌شوند و آن‌ها را بازنویسی می‌کنند. این امکان در تست‌ها برای استفاده از فایل موقت، ساعت کنترل‌شده و کلید نشست مشخص به کار می‌رود. تنظیم `TESTING=True` در این پروژه بررسی CSRF را غیرفعال نمی‌کند.

| تنظیم | مقدار پیش‌فرض | کاربرد |
|---|---|---|
| `SECRET_KEY` | متغیر `QUIZ_SECRET_KEY` یا مقدار تصادفی | امضای کوکی نشست |
| `SESSION_COOKIE_HTTPONLY` | `True` | جلوگیری از خواندن کوکی نشست توسط جاوااسکریپت صفحه |
| `SESSION_COOKIE_SAMESITE` | `"Strict"` | محدودکردن ارسال کوکی در درخواست‌های بین سایت‌ها |
| `SESSION_COOKIE_SECURE` | نتیجهٔ `QUIZ_HTTPS == "1"` | ارسال کوکی فقط روی HTTPS در صورت فعال‌بودن |
| `MAX_CONTENT_LENGTH` | `4096` بایت | سقف حجم بدنهٔ درخواست |
| `QUESTIONS_PATH` | `QUESTIONS_PATH` از `storage.py` | مسیر بانک سؤال |
| `LEADERBOARD_PATH` | `LEADERBOARD_PATH` از `storage.py` | مسیر فایل JSON جدول امتیازها |
| `LOG_PATH` | `quiz_web.log` کنار `web.py` | مسیر لاگ وب؛ مقدار `None` ساخت هندلر فایل جدید را رد می‌کند |
| `MATCH_TTL` | `7200` ثانیه | مهلت نگهداری بازی پس از آخرین دسترسی به وضعیت آن |
| `MAX_MATCHES` | `512` | سقف تعداد بازی‌های نگهداری‌شده در حافظه |
| `CLOCK` | `time.monotonic` | تابع ساعت برای اندازه‌گیری زمان پاسخ |

تنظیم `app.json.ensure_ascii = False` باعث می‌شود حروف فارسی در JSON به شکل خوانا ارسال شوند.

ساخت نمونهٔ جدید برنامه، مخزن بازی مستقلی ایجاد می‌کند. بازی‌های فعال در حافظه‌اند و در کوکی ذخیره نمی‌شوند؛ جدول امتیازها از فایل خوانده می‌شود. برنامه باید با یک process اجرا شود تا همهٔ درخواست‌ها به همان مخزن بازی و قفل دسترسی به جدول امتیازها برسند.

## توابع پردازش درخواست و پاسخ

### prepare_request

```python
def prepare_request():
```

با دکوراتور `@app.before_request` ثبت شده است. ورودی صریح ندارد و اطلاعات درخواست جاری را از Flask می‌خواند. در مسیر عادی چیزی برنمی‌گرداند و اجرای درخواست ادامه می‌یابد.

برای هر درخواست دو مقدار در `g` می‌گذارد:

- `g.request_id`: شناسهٔ تصادفی ۱۲ نویسه‌ای برای پیگیری درخواست.
- `g.started_at`: زمان شروع پردازش با `time.monotonic()` برای محاسبهٔ مدت پاسخ‌گویی.

`g` فضای دادهٔ همان درخواست است. در مقابل، `session` اطلاعات نشست مرورگر را میان درخواست‌ها نگه می‌دارد.

اگر مسیر با `/api/` شروع شود و روش درخواست `POST` باشد، این تابع ابتدا توکن نشست را با هدر `X-CSRF-Token` مقایسه می‌کند. مقایسه با `secrets.compare_digest` انجام می‌شود. سپس بررسی می‌کند که نوع محتوای درخواست JSON باشد.

| وضعیت | خطا |
|---|---|
| توکن وجود ندارد یا مطابقت ندارد | `GameError` با وضعیت `403` و کد `csrf` |
| نوع محتوا JSON نیست | `GameError` با وضعیت `415` و کد `invalid_json` |

درستی ساختار JSON در این مرحله بررسی نمی‌شود؛ خواندن و اعتبارسنجی ساختار به `payload` واگذار شده است. چون بررسی توکن زودتر انجام می‌شود، درخواست فاقد توکن حتی اگر بدنهٔ نامعتبر داشته باشد ابتدا خطای `403` می‌گیرد.

### complete_request

```python
def complete_request(response):
```

با `@app.after_request` ثبت شده است. یک پاسخ Flask می‌گیرد، هدرهای آن را تنظیم می‌کند، خلاصهٔ درخواست را در لاگ ثبت می‌کند و همان پاسخ را برمی‌گرداند. این مرحله روی پاسخ‌های موفق و پاسخ‌های ساخته‌شده توسط توابع مدیریت خطا اجرا می‌شود.

| هدر | مقدار یا کاربرد |
|---|---|
| `X-Request-ID` | مقدار `g.request_id` برای ارتباط پاسخ با لاگ |
| `X-Content-Type-Options` | مقدار `nosniff` |
| `Referrer-Policy` | مقدار `same-origin` |
| `X-Frame-Options` | مقدار `DENY` برای جلوگیری از نمایش صفحه در frame |
| `Content-Security-Policy` | محدودکردن منابع صفحه به همان مبدأ، جلوگیری از frame و محدودکردن مبنای URL و مقصد فرم |
| `Cache-Control` | مقدار `no-store` فقط برای `/` و مسیرهای شروع‌شونده با `/api/` |

لاگ این تابع در سطح `INFO` شامل شناسهٔ درخواست، روش HTTP، مسیر بدون query string، وضعیت پاسخ و مدت پردازش بر حسب میلی‌ثانیه است. بدنهٔ درخواست، کوکی و توکن CSRF را ثبت نمی‌کند. این مدت از ورود درخواست به Flask محاسبه می‌شود و زمان رفت‌وبرگشت شبکهٔ مرورگر را شامل نمی‌شود.

## توابع مدیریت خطا

### game_error

```python
def game_error(error):
```

خطاهای `GameError` را به پاسخ JSON تبدیل می‌کند. این خطاها برای وضعیت‌های قابل پیش‌بینی، مانند نام نامعتبر، نوبت قدیمی یا نبود بازی فعال، استفاده می‌شوند.

ورودی یک `GameError` است که پیام، `code` و `status` دارد. خروجی یک زوج شامل پاسخ JSON و `error.status` است. کد خطا با سطح `WARNING` در لاگ ثبت می‌شود.

```json
{
  "error": {
    "code": "stale_turn",
    "message": "وضعیت بازی تغییر کرده است؛ صفحه را تازه کنید.",
    "request_id": "a1b2c3d4e5f6"
  }
}
```

وضعیت این نمونه `409` است. شناسهٔ درخواست در هدر `X-Request-ID` نیز برمی‌گردد.

### http_error

```python
def http_error(error):
```

خطاهای `werkzeug.exceptions.HTTPException` را پردازش می‌کند؛ برای نمونه خطای مسیر ناموجود، روش HTTP نامجاز، JSON ناقص یا بدنهٔ بیش از حد بزرگ.

خروجی، پاسخ JSON با `code="http_error"` همراه با همان وضعیت HTTP خطاست. برای وضعیت‌های `400`، `404`، `405` و `413` پیام فارسی اختصاصی دارد و برای بقیه از پیام عمومی استفاده می‌کند. پاسخ شامل `request_id` است. این تابع مستقیماً لاگ خطا نمی‌نویسد؛ خلاصهٔ درخواست در `complete_request` ثبت می‌شود.

### unexpected_error

```python
def unexpected_error(error):
```

خطاهای غیرمنتظره‌ای را می‌گیرد که به دو دستهٔ قبلی تعلق ندارند. خروجی همیشه پاسخ JSON با وضعیت `500`، کد `internal_error`، پیام عمومی فارسی و شناسهٔ درخواست است.

این تابع با `logger.exception` جزئیات خطا و traceback را در لاگ ثبت می‌کند؛ متن خطای داخلی را به مرورگر ارسال نمی‌کند. هنگام بررسی مشکل، `request_id` پاسخ را در `quiz_web.log` جست‌وجو کنید.

## توابع مسیرهای وب و API

| تابع | روش | مسیر | وضعیت موفق |
|---|---|---|---|
| `index` | `GET` | `/` | `200` |
| `state` | `GET` | `/api/state` | `200` |
| `create_match` | `POST` | `/api/matches` | `201` |
| `start` | `POST` | `/api/match/start` | `200` |
| `answer` | `POST` | `/api/match/answer` | `200` |
| `next_round` | `POST` | `/api/match/next` | `200` |

همهٔ درخواست‌های `POST` این جدول به کوکی همان نشست، هدر `X-CSRF-Token` و بدنهٔ JSON نیاز دارند. مقدار توکن با `GET /api/state` دریافت می‌شود. `turn` را نیز از آخرین پاسخ موفق بازی بگیرید و همان مقدار را ارسال کنید؛ مقدار آن را سمت کاربر نسازید.

### state

```python
def state():
```

اگر نشست هنوز `csrf_token` نداشته باشد، با `secrets.token_urlsafe(32)` آن را ایجاد می‌کند. اگر نشست شناسهٔ بازی داشته باشد، وضعیت را از `store.state` می‌خواند. خروجی شامل `match`، `rules`، `leaderboard`، `csrf_token` و `expired` است.

|---|---|---|

این مسیر فقط خواندن دادهٔ ثابت نیست: `GameStore` هنگام خواندن وضعیت می‌تواند پایان زمان نوبت را ثبت کند یا ذخیرهٔ ناموفق نتیجهٔ نهایی را دوباره امتحان کند. بازی زمان‌سنج پس‌زمینهٔ مستقلی ندارد؛ پایان زمان در اولین دسترسی بعدی به بازی اعمال می‌شود.

گزینهٔ معتبر یکی از رشته‌های دقیق `A`، `B`، `C` یا `D` است؛ حروف کوچک پذیرفته نمی‌شوند. `choice: null` پیش از پایان زمان با `409` و کد `time_remaining` رد می‌شود. پس از پایان زمان، مخزن ابتدا نوبت را به‌عنوان دیرکرد می‌بندد و برای همان `turn` وضعیت فعلی را برمی‌گرداند.

زمان پاسخ با ساعت سرور محاسبه می‌شود. فیلدهایی مثل `elapsed` یا `points` که کاربر به بدنه اضافه کند، در محاسبه نقشی ندارند.

پس از پاسخ بازیکن اول، نوبت بازیکن دوم با مرحلهٔ `ready` آماده می‌شود؛ امتیاز راند و پاسخ درست هنوز آشکار نمی‌شوند. پس از نوبت هر دو نفر، موتور نتیجهٔ راند را محاسبه می‌کند و مرحله `round_result` یا در راند آخر `finished` می‌شود. تکرار یک پاسخ معتبر با همان `turn`، پاسخ قبلی را عوض نمی‌کند و امتیاز اضافه نمی‌دهد.

## شکل وضعیت بازی

فیلدهای وضعیت را `GameStore` می‌سازد و توابع مسیر `web.py` آن‌ها را در کلید `match` قرار می‌دهند.

| مرحله یا شرط | فیلدها |
|---|---|
| همهٔ بازی‌های موجود | `phase`، `round`، `turn`، `players`، `scores`، `active_player` و `player_index` |
| `answering` | علاوه بر فیلدهای مشترک، `question` و `remaining_seconds` |
| `round_result` یا `finished` | علاوه بر فیلدهای مشترک، `correct`، `correct_text` و `results` |
| `finished` | `winner` و `recorded`؛ در خطای ذخیره، `warning` هم وجود دارد |

`question` شامل `text`، `options` و `power_up` است. `results` برای هر بازیکن شامل `status`، `points`، `choice` و `elapsed` است. وضعیت پاسخ یکی از `correct`، `wrong` یا `too_late` خواهد بود. `player_index` از صفر شروع می‌شود و `round` از یک. `winner: null` به معنی تساوی است.

در مرحلهٔ `finished`، مقدار `recorded: false` یعنی نتیجهٔ بازی مشخص شده اما نوشتن جدول امتیازها ناموفق بوده است؛ پاسخ بازی همچنان موفق است و هشدار در `match.warning` می‌آید.

## کدهای خطای API

| وضعیت HTTP | کد JSON | علت رایج |
|---|---|---|
| `400` | `invalid_request` | نام یا گزینهٔ نامعتبر، نبود `choice`، یا JSON با ساختار غیر object |
| `400` | `http_error` | JSON ناقص |
| `403` | `csrf` | نبود یا نامعتبر بودن توکن CSRF |
| `404` | `match_expired` | بازی نشست هنگام انجام عملیات پیدا نمی‌شود |
| `404` | `http_error` | مسیر ناموجود |
| `405` | `http_error` | روش HTTP نامجاز برای مسیر |
| `409` | `stale_turn` | مقدار `turn` نامعتبر یا ناسازگار با وضعیت بازی |
| `409` | `invalid_phase` | عملیات با مرحلهٔ فعلی بازی سازگار نیست |
| `409` | `time_remaining` | ارسال `choice: null` پیش از پایان زمان |
| `413` | `http_error` | بدنهٔ درخواست بیش از ۴۰۹۶ بایت |
| `415` | `invalid_json` | نوع محتوای درخواست JSON نیست |
| `500` | `internal_error` | خطای غیرمنتظره |
| `503` | `question_bank` | بانک سؤال مفقود، نامعتبر، غیرقابل خواندن یا فاقد سؤال کافی |
| `503` | `capacity` | ظرفیت نگهداری بازی‌ها پر شده است |

ردشدن یک درخواست ممکن است چند علت داشته باشد؛ پاسخی که دریافت می‌شود به ترتیب بررسی‌ها و وضعیت فعلی بازی بستگی دارد. برای نمونه، نبود توکن پیش از اعتبارسنجی نام‌ها بررسی می‌شود و `state` خطای نبود بازی نشست را به پاسخ موفق با `expired: true` تبدیل می‌کند.

## اجرای مستقیم و تابع serve

```python
if __name__ == "__main__":
    from waitress import serve

    app = create_app()
    host = os.environ.get("QUIZ_HOST", "127.0.0.1")
    port = int(os.environ.get("QUIZ_PORT", "8000"))
    print(f"Quiz Battle: http://{host}:{port}", flush=True)
    serve(app, host=host, port=port, threads=8)
```

این بخش تنها با اجرای مستقیم فایل، مانند `python web.py`، اجرا می‌شود. دستور `from web import create_app` آن را اجرا نمی‌کند؛ به همین دلیل تست‌ها می‌توانند برنامه را بدون بازکردن پورت بسازند.

`serve` تابع واردشده از Waitress است و در `web.py` تعریف نشده است. این تابع برنامهٔ Flask را از طریق رابط WSGI اجرا می‌کند: درخواست HTTP را به برنامه تحویل می‌دهد و پاسخ برنامه را به مرورگر برمی‌گرداند. اجرای آن تا توقف سرور، مثلاً با `Ctrl+C`، ادامه دارد.

| آرگومان | مقدار این پروژه | توضیح |
|---|---|---|
| `app` | خروجی `create_app()` | برنامه‌ای که درخواست‌ها را پردازش می‌کند |
| `host` | `QUIZ_HOST` یا `127.0.0.1` | آدرس گوش‌دادن؛ پیش‌فرض فقط از همان دستگاه قابل دسترسی است |
| `port` | تبدیل عددی `QUIZ_PORT` یا `8000` | پورت دریافت درخواست‌ها |
| `threads` | `8` | تعداد رشته‌های پردازش درخواست؛ تعداد بازیکن‌ها را تعیین نمی‌کند |

متغیرهای `QUIZ_HOST` و `QUIZ_PORT` فقط در بخش اجرای مستقیم خوانده می‌شوند. `create_app(config)` به‌تنهایی از آن‌ها برای ایجاد سرور استفاده نمی‌کند.

توابع مدیریت خطای Flask مربوط به درخواست‌ها هستند. خطای راه‌اندازی، مانند غیرعددی‌بودن `QUIZ_PORT` یا اشغال‌بودن پورت، در این بخش به پاسخ JSON تبدیل نمی‌شود و در خروجی اجرای برنامه دیده می‌شود. چاپ آدرس با `print` نیز پیش از فراخوانی `serve` انجام می‌شود و به‌تنهایی موفقیت بازشدن پورت را تأیید نمی‌کند.

## نمونهٔ استفاده بدون اجرای سرور

نمونهٔ زیر از کلاینت تست Flask استفاده می‌کند؛ کوکی نشست را خود کلاینت نگه می‌دارد. جدول امتیازها در پوشهٔ موقت قرار می‌گیرد و فایل اصلی پروژه تغییر نمی‌کند. کد را از پوشهٔ اصلی پروژه و با وابستگی‌های نسخهٔ وب اجرا کنید.

```python
from pathlib import Path
from tempfile import TemporaryDirectory

from web import create_app

with TemporaryDirectory() as temporary:
    app = create_app({
        "TESTING": True,
        "SECRET_KEY": "documentation-example-only",
        "QUESTIONS_PATH": Path("questions.json").resolve(),
        "LEADERBOARD_PATH": Path(temporary) / "leaderboard.json",
        "LOG_PATH": None,
    })
    client = app.test_client()

    # دریافت توکن و ایجاد نشست مرورگر
    initial = client.get("/api/state").get_json()
    headers = {"X-CSRF-Token": initial["csrf_token"]}

    # ساخت بازی در مرحلهٔ ready
    response = client.post(
        "/api/matches",
        json={"players": ["سارا", "علی"]},
        headers=headers,
    )
    assert response.status_code == 201
    match = response.get_json()["match"]
    assert match["phase"] == "ready"

    # شروع نوبت بازیکن اول و زمان پاسخ او
    response = client.post(
        "/api/match/start",
        json={"turn": match["turn"]},
        headers=headers,
    )
    assert response.status_code == 200
    match = response.get_json()["match"]
    assert match["phase"] == "answering"
    print(match["question"]["text"])

    # ثبت یک گزینه؛ درست یا غلط بودن بعد از نوبت هر دو نفر آشکار می‌شود
    response = client.post(
        "/api/match/answer",
        json={"turn": match["turn"], "choice": "A"},
        headers=headers,
    )
    assert response.status_code == 200
    match = response.get_json()["match"]
    assert match["phase"] == "ready"
    assert match["player_index"] == 1
    assert "correct" not in match
```

برای ادامه، از `turn` آخرین پاسخ برای شروع نوبت نفر دوم و ثبت پاسخ او استفاده کنید. بعد از مرحلهٔ `round_result`، درخواست `/api/match/next` راند بعد را آماده می‌کند. تست‌های [test_web.py](../tests/test_web.py) نمونهٔ اجرای کل پنج راند، پایان زمان، درخواست تکراری و مدیریت خطا را پوشش می‌دهند.
