# ۰ تا ۵ — 🏁 گرم‌کردن

**مسابقه‌ی راه‌اندازی، دور سوم.** زمان‌ها را با هفته‌ی پیش مقایسه و بلند اعلام کنید.

**دو میان‌بُر هفته** — امروز مدام بین VS Code و مرورگر جابه‌جا می‌شوند، پس این دو دقیقاً به‌جا هستند:

| کلید | چه می‌کند |
|---|---|
| `Win + ← / →` | پنجره را نصف صفحه می‌کند — **VS Code یک طرف، GitHub طرف دیگر** |
| `Alt + Tab` | جابه‌جایی سریع بین دو پنجره |

روی گوشه‌ی تخته بنویسید و هر بار که دیدید کسی با ماوس پنجره‌ها را جابه‌جا می‌کند، یادآوری کنید.

# ۱۰ تا ۳۵ — ⏳ سفر در زمان: بقیه‌ی git محلی

**جمله‌ی افتتاح این بلوک:**

> «هفته‌ی پیش یاد گرفتیم save کنیم و به **آخرین** save برگردیم. امروز یاد می‌گیریم
> در تاریخچه **قدم بزنیم** — هر save، هر چند هفته عقب.»

## دقیقه‌ی ۱۰ تا ۱۵ — `git diff`: چه چیزی عوض شده؟

یک تغییر کوچک در `game.py` بدهند (یک پیام را عوض کنند) و **ذخیره نکنند commit**:

```bat
git status
git diff
```

`status` می‌گوید **کدام فایل** عوض شده. `diff` می‌گوید **چه چیزی** عوض شده:

```diff
- console.print("✅ درست!", style="bold green")
+ console.print("✅ آفرین!", style="bold green")
```

> «خط با `-` چیزی است که بود، خط با `+` چیزی است که شد. **قبل از هر commit یک `git diff`
> بزن** — این عادت، نصف اشتباه‌ها را می‌گیرد: `print` دیباگی جامانده، خطی که اشتباهی پاک شده.»

⚠️ یادآوری: `git diff` هم صفحه‌ی pager باز می‌کند → **`q`** برای بستن.

**مقایسه با VS Code:** نوار رنگی کنار شماره‌ی خط را نشان بدهید.
> «`git diff` **می‌گوید**، VS Code **نشان می‌دهد**. همان چیزند، دو زبان.»

## دقیقه‌ی ۱۵ تا ۲۰ — `git log` عمیق‌تر و `git show`

```bat
git log --oneline           ← که بلدید
git log --oneline --stat    ← هر commit چه فایل‌هایی را دست زد
git log --oneline -p        ← کل تغییرهای هر commit، خط‌به‌خط
```

و برای یک commit مشخص (hash را از `log --oneline` بردارند):

```bat
git show 3f2a1b9
```

> «الان می‌توانی بپرسی: **آن روز دقیقاً چه کار کردم؟** و git جواب می‌دهد.»

سؤال از کلاس: «چرا پیام‌های commit خوب مهم بودند؟» — و بگذارید خودشان جواب بدهند:
چون `git log --oneline` بدون پیام معنادار، فقط یک مشت hash است.

## دقیقه‌ی ۲۰ تا ۲۸ — ⭐ `git restore --source` : برگشتن به یک commit **قدیمی**

**این ستاره‌ی بلوک است.** هفته‌ی پیش `git restore game.py` را زدند و به **آخرین** commit
برگشتند. امروز:

```bat
git log --oneline
git restore --source=<hash قدیمی> -- game.py
```

**فعالیت (این را واقعاً انجام دهند، نه فقط نگاه کنند):**

1. `git log --oneline` — hash یک commit **چند هفته قبل** را بردارند
   (مثلاً commit قبل از رنگی‌شدن بازی)
2. `git restore --source=<آن hash> -- game.py`
3. `python game.py` → **رنگ‌ها رفته‌اند!** بازی به نسخه‌ی قدیمی برگشته
4. بگذارید کمی وحشت کنند 😄 بعد:
5. `git restore game.py` → همه‌چیز برگشت

> «فرقش را ببینید:
> `git restore game.py` = برگرد به **آخرین** save.
> `git restore --source=<hash> -- game.py` = برگرد به **آن** save.»

**نکته‌ی مهم که باید صریح بگویید:**
> «این دستور **تاریخچه را پاک نمی‌کند.** فقط فایل روی دیسک را عوض می‌کند. تاریخچه
> دست‌نخورده سر جایش است — می‌توانی هر لحظه برگردی.»

🌱 و یک جمله برای زندگی واقعی‌شان: «هفته‌ی پیش خودِ من با همین دستور، پوشه‌های پاک‌شده‌ی
درس‌ها را برگرداندم.» (داستان واقعی همیشه بهتر از مثال است.)

## دقیقه‌ی ۲۸ تا ۳۳ — `git revert`: بی‌اثر کردن یک commit

سناریو: «یک commit زدی، بعد فهمیدی کل آن تغییر اشتباه بود.»

```bat
git revert <hash>
```

> «git یک commit **جدید** می‌سازد که دقیقاً کارِ آن commit را برمی‌گرداند.
> تاریخچه پاک نمی‌شود — به آن **اضافه** می‌شود. مثل اینکه در دفترت بنویسی
> "صفحه‌ی قبل را باطل کردم"، نه اینکه صفحه را پاره کنی.»

فقط مربی روی پرده نشان دهد (۳ دقیقه) — لازم نیست همه بزنند.
اگر ویرایشگر پیام باز شد: `Esc` بعد `:wq` — یا از قبل `git revert --no-edit <hash>` بزنید.

## دقیقه‌ی ۳۳ تا ۳۵ — سه ابزار، سه کار متفاوت (خلاصه روی تخته)

| دستور | چه می‌کند | تاریخچه؟ |
|---|---|---|
| `git restore <file>` | فایل را به آخرین commit برگردان | دست‌نخورده |
| `git restore --source=<hash> -- <file>` | فایل را به **آن** commit برگردان | دست‌نخورده |
| `git revert <hash>` | یک commit جدید که کار آن commit را باطل می‌کند | یک commit **اضافه** می‌شود |

**⚠️ نکته‌ی مربی — این را به بچه‌ها یاد ندهید:** `git reset --hard`.
اگر کسی از اینترنت پیدایش کرد: «هست، ولی تاریخچه را واقعاً پاک می‌کند. دو جلسه‌ی دیگر.»

# ۳۵ تا ۴۰ — git ≠ GitHub

**رایج‌ترین سوءتفاهم دنیای برنامه‌نویسی.** صریح و کوتاه:

> «**git** یک **برنامه** است روی لپ‌تاپ تو. تا امروز همه‌ی کارهایمان با git بود و
> **یک بایت هم به اینترنت نرفت.**
>
> **GitHub** یک **سایت** است — خانه‌ای در اینترنت برای repoها. مثل اینکه آلبوم عکست
> را در یک گاوصندوق اینترنتی هم بگذاری.»

روی تخته سه دلیل بنویسید:

| چرا GitHub؟ | |
|---|---|
| 🛡 **پشتیبان** | لپ‌تاپ خراب شود، پوشه پاک شود — کارت سالم است |
| 🤝 **کار تیمی** | هر دو عضو تیم روی یک کد کار می‌کنند |
| 🌍 **نمونه‌کار** | آخر دوره این آدرس بخشی از رزومه‌ی شماست |

دلیل اول را با داستان واقعی بگویید — بچه‌ها این هفته حتماً یکی‌شان کاری را از دست داده.

# ۴۰ تا ۶۵ — ☁️ پروژه روی GitHub

## ⚠️ ترتیب کارها را دقیقاً رعایت کنید

**عضو اول هر تیم** repo را می‌سازد. عضو دوم فعلاً تماشا می‌کند (نوبتش دقیقه‌ی ۶۵ است).

## دقیقه‌ی ۴۰ تا ۴۵ — ساخت repo (عضو اول)

روی github.com → دکمه‌ی **+** بالا راست → **New repository**

| گزینه | مقدار | چرا |
|---|---|---|
| Repository name | `quiz-battle` | |
| Description | یک جمله فارسی یا انگلیسی | |
| Public / Private | **Private** | فعلاً خصوصی؛ جلسه‌ی ۱۱ عمومی می‌شود |
| Add a README file | ⛔ **تیک نزنید** | |
| Add .gitignore | ⛔ **تیک نزنید** | |
| Choose a license | ⛔ **هیچ‌کدام** | |

**🚨 این مهم‌ترین تله‌ی امروز است.** اگر repo با README ساخته شود، اولین `push` رد می‌شود
و پیام گیج‌کننده‌ی `rejected — non-fast-forward` می‌گیرند. **repo باید کاملاً خالی باشد.**
این را دو بار بگویید و روی پرده نشان بدهید.

## دقیقه‌ی ۴۵ تا ۴۷ — 📨 دعوت عضو دوم را **همین حالا** بفرستید

repo → **Settings** → **Collaborators** → **Add people** → نام کاربری عضو دوم

> **چرا الان؟** چون قبول‌کردن دعوت چند دقیقه طول می‌کشد. تا دقیقه‌ی ۶۵ که نوبت عضو دوم
> می‌شود، دعوت قبول شده است. اگر این کار را دقیقه‌ی ۶۵ بکنید، ۱۰ دقیقه معطل می‌مانید.

عضو دوم همان لحظه در مرورگر خودش می‌رود سراغ **زنگ اعلان‌ها** یا ایمیلش و قبول می‌کند.

## دقیقه‌ی ۴۷ تا ۶۰ — وصل‌کردن و اولین push

GitHub خودش دستورها را نشان می‌دهد. سه خط، در ترمینال پوشه‌ی پروژه:

```bat
git remote add origin https://github.com/USERNAME/quiz-battle.git
git branch -M main
git push -u origin main
```

**توضیح هر خط (مهم — طوطی‌وار نزنند):**

- `remote add origin ...` — «به git می‌گویی: خانه‌ی اینترنتی‌ات اینجاست. `origin`
  فقط یک **اسم مستعار** برای آن آدرس است تا هر بار آدرس بلند را تایپ نکنی.»
- `git branch -M main` — «مطمئن می‌شویم اسم شاخه‌ی اصلی `main` است، همان چیزی که GitHub می‌خواهد.»
- `push -u origin main` — «هُلش بده بالا. `-u` یعنی از این به بعد فقط `git push` کافی است.»

**🔐 پنجره‌ی ورود:** اولین `push` یک پنجره باز می‌کند و می‌گوید با مرورگر وارد GitHub شوید
→ **Authorize**. یک‌بار برای همیشه.
⚠️ **اگر رمز عبور خواست، رمز را نزنید** — GitHub رمز را قبول نمی‌کند. جدول مشکلات انتهای سند.

**بعد از push، صفحه‌ی repo را در مرورگر refresh کنند.** اینجا مکث کنید:

> «نگاه کنید. `game.py` آنجاست. `requirements.txt` آنجاست. و روی تب **Commits**…
> **همان تاریخچه‌ای که هفته‌ی پیش در ترمینال دیدید.** با همان پیام‌هایی که خودتان نوشتید.
> کدتان الان روی اینترنت است.»

بگذارید یک دقیقه repo خودشان را بگردند: فایل‌ها، commitها، کلیک روی یک commit و دیدن diff.

> «این همان `git show` است — فقط با ماوس.»

## دقیقه‌ی ۶۰ تا ۶۵ — چرخه‌ی روزانه

روی تخته، بزرگ:

```
pull  →  کار  →  commit  →  push
```

- `git pull` — «اول ببین دیگری چه فرستاده»
- `git push` — «آخر، کارت را بفرست»

> «این چرخه را تا آخر دوره ده‌ها بار تکرار می‌کنید. مثل مسابقه‌ی راه‌اندازی —
> باید بدون فکر کردن انجامش بدهید.»

# ۶۵ تا ۸۰ — 🤝 عضو دوم `clone` می‌کند

**این پاداش نظم جلسه‌ی ۲ است. از دستش ندهید.**

عضو دوم، در یک پوشه‌ی **کاملاً جدید** (مثلاً `C:\dev\`):

```bat
cd C:\dev
git clone https://github.com/USERNAME/quiz-battle.git
cd quiz-battle
python -m venv venv
venv\Scripts\activate
pip install -r requirements.txt
python game.py
```

**بازی روی لپ‌تاپ دوم بالا می‌آید.** اینجا بلند تحسین کنید:

> «شش دستور. **پروژه‌ای که خودش ننوشته بود، روی لپ‌تاپ خودش اجرا شد.**
> یادتان هست جلسه‌ی ۲ پرسیدم "اگر فایل را برای هم‌تیمی‌ات بفرستی و اجرا نشود چه؟"
> **این جوابش بود.** آن `requirements.txt` که دو هفته پیش ساختید، الان کارش را کرد.»

بپرسید: **«چرا پوشه‌ی `venv` در آنچه clone شد نبود؟»** → `.gitignore`. حلقه بسته می‌شود.

## دقیقه‌ی ۷۳ تا ۸۰ — رفت و برگشت واقعی

حالا **عضو دوم** یک تغییر کوچک می‌دهد و می‌فرستد:

```bat
git add .
git commit -m "Add two science questions"
git push
```

و **عضو اول**:

```bat
git pull
```

**تغییرِ هم‌تیمی‌اش روی لپ‌تاپ خودش ظاهر می‌شود.** این لحظه را هم بزرگ کنید:

> «الان دو نفر روی یک کد کار می‌کنید. این همان چیزی است که در شرکت‌های نرم‌افزاری
> هر روز اتفاق می‌افتد — با همین دو دستور.»

اگر وقت بود، یک دور دیگر در جهت مخالف (عضو اول تغییر بدهد، عضو دوم pull کند).

# ۸۰ تا ۸۵ — 🎁 کششی: `branch` چیست؟

**فقط معرفی، بدون تمرین.** جلسه‌ی ۸ کاملش می‌کنیم.

```bat
git switch -c feature/new-questions     ← میز کار شخصی بساز
   ... کار و commit ...
git switch main                          ← برگرد به ویترین
git merge feature/new-questions          ← کارت را بیاور روی ویترین
```

> «`main` **ویترین نمایشگاه** است — همیشه سالم و قابل‌بازی.
> `branch` **میز کار شخصی** توست — هر چه خواستی خراب کن، تا خودت نخواهی به ویترین نمی‌رسد.»

قانون تیمی را اعلام کنید (ولی هنوز اجرایش نکنید):
> «از جلسه‌ی ۸: روی `main` مستقیم کار نمی‌کنیم.»

# ۸۵ تا ۹۰ — قانون جدید و تمرین خانه

**قانون تازه‌ی دوره، روی پوستر:**

> ## قانون ۵: هر جلسه با `push` تمام می‌شود.

و دلیلش را با صداقت بگویید:

> «تا امروز اگر لپ‌تاپت خراب می‌شد، یک هفته کار را از دست می‌دادی. از امروز، **صفر**.
> کدتان دو جا هست: لپ‌تاپ شما و اینترنت.»

تمرین خانه را پخش کنید و جمله‌ی آخر:

> «یادتان هست جلسه‌ی ۱ پرسیدم "خواهر کوچکت که برنامه‌نویس نیست چطور به بازی‌ات
> سؤال اضافه کند؟" **جلسه‌ی بعد حلش می‌کنیم:** سؤال‌ها از دل کد بیرون می‌آیند و
> رده‌بندی بین اجراها می‌ماند. با پروژه‌ی push‌شده بیایید.»

# چک‌لیست پایان جلسه

- [ ] هر دانش‌آموز `git diff` را یک‌بار زده و خروجی‌اش را خوانده
- [ ] **هر دانش‌آموز `git restore --source=<hash>` را روی فایل خودش تجربه کرده**
      و بعد برگشته — این ستاره‌ی بلوک اول است
- [ ] **هر تیم یک repo روی GitHub دارد** و `push` موفق بوده
- [ ] عضو دوم هر تیم collaborator شده و دعوت را **قبول** کرده
- [ ] **عضو دوم `clone` کرده و بازی روی لپ‌تاپ خودش اجرا شده**
- [ ] حداقل یک رفت‌وبرگشت `push` / `pull` بین دو عضو انجام شده
- [ ] قانون ۵ روی پوستر اضافه شد
- [ ] **آدرس repo همه‌ی تیم‌ها را جایی یادداشت کرده‌اید** ← تا آخر دوره لازمتان می‌شود

> repo هر تیم روی GitHub است، هر دو عضو حداقل یک‌بار `push` کرده‌اند، عضو دوم پروژه را

# 🪜 نردبان حذف

1. ~~`git log -p` و `--stat`~~ → فقط `--oneline` و `git show` (۳ دقیقه)
2. ~~معرفی `branch`~~ → کامل به جلسه‌ی ۸ (۵ دقیقه)
3. ~~`git revert`~~ → جلسه‌ی ۹، وقتی باگ واقعی دارند (۵ دقیقه)
4. ~~رفت‌وبرگشت دوم push/pull~~ → تمرین خانه (۴ دقیقه)
5. ~~`git diff` مقایسه با VS Code~~ (۲ دقیقه)

**سه چیزی که هرگز حذف نمی‌شوند:**
- **`git restore --source`** — تنها ابزار واقعی «سفر در زمان» که امروز یاد می‌گیرند
- **`push` موفق هر تیم** — بدون این، قانون ۵ و بیمه‌ی کل دوره ساخته نمی‌شود
- **`clone` عضو دوم** — پاداش جلسه‌ی ۲ و شروع هویت تیمیِ دوره

**اگر اینترنت خراب شد یا احراز هویت گیر کرد:** بلوک GitHub را به ابتدای جلسه‌ی ۵ منتقل
کنید (۲۵ دقیقه) و امروز بلوک git محلی را عمیق‌تر کار کنید + `branch` و `merge` را
کامل تمرین کنید (هیچ‌کدام اینترنت لازم ندارند).

# 🔌 پلن B آفلاین: «GitHub روی فلش»

اگر اینترنت کلاس قطع شد، مفهوم را **بدون اینترنت** درس بدهید. روی یک فلش:

```bat
:: عضو اول — یک «خانه‌ی مشترک» روی فلش بساز
cd D:\
git clone --bare C:\dev\quiz-battle quiz-battle.git

:: و پروژه‌ی خودش را به آن وصل کن
cd C:\dev\quiz-battle
git remote add origin D:\quiz-battle.git
git push -u origin main

:: عضو دوم — از فلش clone کن
cd C:\dev
git clone D:\quiz-battle.git quiz-battle
```

> «دقیقاً همان چیزی است که GitHub می‌کند — فقط خانه‌ی مشترک روی فلش است، نه اینترنت.
> `push` و `pull` و `clone`، همه عین همان.»

**این پلن B واقعاً خوب است** چون مفهوم `remote` را از «یک سایت جادویی» به
«یک پوشه‌ی مشترک» تبدیل می‌کند. حتی اگر اینترنت سالم بود، ۳ دقیقه نشان‌دادنش ارزش دارد.

# مشکلات و راه‌حل آماده

## GitHub و احراز هویت

| پیام / نشانه | علت | راه‌حل |
|---|---|---|
| `Support for password authentication was removed` | رمز عبور GitHub را زده | رمز کار نمی‌کند. پنجره‌ی مرورگر باید باز شود → Authorize. اگر نشد: GitHub → Settings → Developer settings → **Personal access tokens (classic)** → Generate → scope: `repo` → توکن را **به‌جای رمز** بزنید |
| پنجره‌ی ورود باز نمی‌شود | Git Credential Manager نصب نیست | Git for Windows را با گزینه‌ی پیش‌فرض دوباره نصب کنید (چک‌لیست آماده‌سازی) |
| `remote: Repository not found` | آدرس غلط، یا collaborator نیست | آدرس را از دکمه‌ی سبز **Code** روی GitHub کپی کنند؛ دعوت قبول شده باشد |
| `Updates were rejected — non-fast-forward` | repo با README ساخته شده | ساده‌ترین راه: repo را پاک کنند و **خالی** بسازند. (یا `git pull --rebase origin main` بعد `push`) |
| `error: remote origin already exists` | دوبار `remote add` زده‌اند | `git remote set-url origin <آدرس>` |
| `src refspec main does not match any` | شاخه `master` است نه `main`، یا هیچ commitی نیست | `git branch -M main` و مطمئن شوند حداقل یک commit دارند |
| `fatal: not a git repository` | ترمینال در پوشه‌ی پروژه نیست | `File → Open Folder` روی پوشه‌ی پروژه |
| clone در پوشه‌ی پروژه‌ی خودش انجام شد | `cd C:\dev` نکرده | پوشه‌ی تودرتو را پاک کند، از `C:\dev` دوباره clone کند |
| بعد از clone `No module named 'rich'` | venv نساخته یا فعال نکرده | چهار دستور راه‌اندازی جلسه‌ی ۲ |

## git محلی

| پیام / نشانه | راه‌حل |
|---|---|
| ترمینال بعد از `git diff` یا `git log` هنگ کرد | کلید **`q`** |
| `git revert` یک ویرایشگر عجیب باز کرد | `Esc` بعد `:wq` — یا از اول `git revert --no-edit <hash>` |
| `git restore --source` گفت `pathspec did not match` | `--` را جا انداخته: `git restore --source=<hash> -- game.py` |
| `error: unknown option 'source'` | نسخه‌ی git قدیمی است | `git checkout <hash> -- game.py` (همان کار) |
| hash را اشتباه تایپ می‌کنند | ۷ کاراکتر اول کافی است؛ از `git log --oneline` کپی کنند (در ترمینال VS Code با ماوس انتخاب و `Ctrl+C`) |
