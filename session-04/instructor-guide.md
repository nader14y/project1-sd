## دقیقه‌ی ۲۵ تا ۳۲ — کلاس `Question`

این را **کامل با هم تایپ کنند** (اسکلتش را پر می‌کنند) — چون `__init__` و `self` مفهوم تازه‌اند:

```python
class Question:
    def __init__(self, text, options, correct):
        self.text = text
        self.options = options      # ۴ گزینه، به ترتیب A تا D
        self.correct = correct      # "A" یا "B" یا "C" یا "D"

    def is_correct(self, choice):
        return choice.strip().upper() == self.correct

    def correct_text(self):
        return self.options["ABCD".index(self.correct)]
```

**سه نکته‌ی گذری:**
- `self` = «خودِ این سؤال». «وقتی صد سؤال داریم، `self` می‌گوید حرف کدامشان است.»
- `.strip().upper()` — همان چیزی که جلسه‌ی ۱ نوشتند، حالا **یک‌جا برای همه‌ی سؤال‌ها**.
  بگویید: «ببینید چه شد — قانون درستیِ جواب فقط در یک نقطه از کل برنامه نوشته شده.»
- `correct_text()` — «متد می‌تواند چیزی برگرداند، نه فقط کاری بکند.»

## دقیقه‌ی ۳۲ تا ۴۵ — `Match`: ساختن، شروع راند، ثبت جواب

```python
class Match:
    def __init__(self, player1, player2, questions):
        if player1 == player2:
            raise ValueError("نام دو بازیکن نمی‌تواند یکی باشد")

        self.players = [player1, player2]
        self.questions = questions
        self.scores = {player1: 0, player2: 0}
        self.round = 0              # ۰ یعنی هنوز شروع نشده
        self.answers = {}           # نام بازیکن → (گزینه، ثانیه)

    def start_round(self):
        self.round += 1
        self.answers = {}
        return self.questions[self.round - 1]

    def submit(self, player, choice, elapsed):
        self.answers[player] = (choice, elapsed)

    def is_over(self):
        return self.round >= ROUNDS

    def winner(self):
        player1, player2 = self.players
        if self.scores[player1] == self.scores[player2]:
            return None
        if self.scores[player1] > self.scores[player2]:
            return player1
        return player2
```

**سه نکته:**
- `raise ValueError(...)` — «موتور اجازه نمی‌دهد مسابقه‌ی بی‌معنا ساخته شود. **فریاد می‌زند.**»
  ⚠️ عمداً در `game.py` مدیریتش نمی‌کنیم — خوراک جلسه‌ی ۹.
- `self.round - 1` — «راند ۱ یعنی سؤال شماره‌ی صفرِ لیست. یک دقیقه روی همین بایستید،
  اینجا جای اشتباه رایج است.»
- `winner()` که `None` برمی‌گرداند — «`None` یعنی "هیچ‌کس". مساوی هم یک جواب است.»

# ۴۵ تا ۶۰ — `resolve_round`: قلب موتور

این سخت‌ترین ۱۵ دقیقه‌ی جلسه است. **چهار مرحله، روی تخته بنویسید قبل از تایپ:**

```
۱) برای هر بازیکن: درست بود؟ غلط بود؟ دیر شد؟
۲) بین درست‌جواب‌ها، سریع‌ترین را پیدا کن → بونوس
۳) امتیازها را به scores اضافه کن
۴) نتیجه را برگردان (چاپ نکن!)
```

```python
    def resolve_round(self):
        question = self.questions[self.round - 1]
        results = {}
        correct_players = []

        # ۱) درست بود، غلط بود، یا دیر؟
        for player in self.players:
            choice, elapsed = self.answers[player]

            if elapsed > TIME_LIMIT:
                results[player] = {"status": "too_late", "points": 0}
            elif question.is_correct(choice):
                results[player] = {"status": "correct", "points": POINTS}
                correct_players.append(player)
            else:
                results[player] = {"status": "wrong", "points": 0}

        # ۲) بونوس سرعت: بین درست‌جواب‌ها، سریع‌ترین
        if correct_players:
            fastest = correct_players[0]
            for player in correct_players:
                if self.answers[player][1] < self.answers[fastest][1]:
                    fastest = player
            results[fastest]["points"] += SPEED_BONUS

        # ۳) امتیازها را جمع کن
        for player in self.players:
            self.scores[player] += results[player]["points"]

        return results
```

**چهار نکته‌ی مهم:**

- **ترتیب `if` مهم است.** بپرسید: «اگر کسی جواب **درست** بدهد ولی در ۳۵ ثانیه، چه می‌شود؟»
  → صفر. «چون اول مهلت را چک می‌کنیم.» این تصمیم را بلند بگویید.
- **`if correct_players:`** — «اگر هر دو غلط بدهند، بونوس به کسی نمی‌رسد.»
  بپرسید: «اگر این `if` نبود چه می‌شد؟» → خطا، چون `correct_players[0]` وجود ندارد.
- **الگوی پیدا کردن کمینه** — «اولی را بردار، بعد هر کس بهتر بود جایش را بگیر.»
  این الگو را بچه‌ها تا آخر عمر لازم دارند.
- **`return results` و نه `print`** — «موتور **نتیجه** می‌دهد؛ جمله‌سازی و رنگ کار دهان است.»
  اینجا به قانون تخته اشاره کنید.

## ۲) تابع `ask` — کرنومتر (۵ دقیقه، مهم‌ترین تابع امروز)

```python
def ask(player, question, round_no):
    console.clear()
    console.print(f"[bold cyan]راند {round_no} از {ROUNDS}[/bold cyan]")
    console.print(f"\n[bold yellow]نوبت {player}[/bold yellow] — ⏱ {TIME_LIMIT} ثانیه فرصت داری!")
    console.print(f"\n{question.text}")
    for letter, option in zip("ABCD", question.options):
        console.print(f"  [bold]{letter})[/bold] {option}")

    start = time.time()                 # ← کرنومتر روشن
    choice = input("\nجواب تو (A-D): ")
    elapsed = time.time() - start       # ← کرنومتر خاموش

    return choice, elapsed
```

انگشتتان را بگذارید روی آن دو خط:
> «کرنومتر **اینجا** است، در دهان — نه در مغز. مغز فقط عدد ثانیه را می‌گیرد.

## بخش ۱ — دلیل واقعی، برای خودتان

### ۱.۱ دلیلِ درست: سرعتِ تغییر، نه مرتب‌بودن

بزرگ‌ترین اشتباه در آموزش این مبحث این است که به‌عنوان «نظم و مرتبی» معرفی شود.
دلیل واقعی این است:

> ## تکه‌های یک برنامه با **سرعت‌های مختلف** و به **دلیل‌های مختلف** عوض می‌شوند.

- قواعد بازی وقتی عوض می‌شوند که بخواهید **بازی** فرق کند (بونوس ۵ شود، سرقت اضافه شود).
- نمایش وقتی عوض می‌شود که بخواهید **قشنگ‌تر** شود (رنگ، نوار، جدول، بعداً پنجره‌ی گرافیکی).

این دو هیچ ربطی به هم ندارند، در **زمان‌های مختلف** عوض می‌شوند، و اغلب توسط
**آدم‌های مختلف**. وقتی در یک فایل باشند، هر دست‌کاری در یکی، ریسکِ خرابیِ آن یکی است.

پس معیار تقسیم، **اندازه نیست**. یک فایل ۴۰ خطی می‌تواند غلط تقسیم شده باشد و یک فایل
۳۰۰ خطی درست باشد. معیار این است:

> ## «چیزهایی که **به یک دلیل** عوض می‌شوند کنار هم؛ چیزهایی که به **دلیل‌های مختلف** عوض می‌شوند، جدا.»

این جمله دقیقاً همان چیزی است که در دنیای حرفه‌ای «اصل مسئولیت واحد» نامیده می‌شود —
ولی این نسخه‌ی درستش است، نه نسخه‌ی «هر فایل کوچک باشد».

### ۱.۲ چهار سود این تقسیم — و اینکه هر کدام کِی نقد می‌شود

این جدول قلب پیوست است. بخوانید و **باور کنید**، چون بچه‌ها امروز فقط سود چهارم را می‌بینند:

| سود | چه می‌گوید | کِی برای بچه‌ها **ثابت** می‌شود |
|---|---|---|
| ۱. **قابل آزمایش‌شدن** | موتوری که `print`/`input` ندارد را می‌شود هزار بار در یک ثانیه اجرا کرد | **جلسه‌ی ۷ (pytest) — قله‌ی دوره** |
| ۲. **تعویض ظاهر** | مغز ثابت، صورت عوض‌شدنی؛ همان بازی با ظاهر تازه | جلسه‌ی ۱۱ (صیقل) |
| ۳. **کار دونفره** | دو نفر در یک فایل به هم می‌خورند؛ در دو فایل نه | جلسه‌ی ۸ (branch و conflict) |
| ۴. **پیدا کردن باگ** | «امتیاز غلط است» → یعنی `engine.py`. «شکل غلط است» → یعنی `game.py` | **همین امروز، دقیقه‌ی ۷۰** |

**نتیجه‌ی آموزشی مهم:** سه سود از چهار سود، **وعده‌ی آینده** است. یعنی امروز شما
نمی‌توانید این تصمیم را با استدلال ببرید — و **نباید هم تلاش کنید**. راهش این است که
سود چهارم را امروز نقداً نشان دهید، و سه سود دیگر را صادقانه به‌عنوان قرض معرفی کنید:

> «امروز فقط یکی از چهار فایده را می‌بینی. سه فایده‌ی دیگر **قرض من به شماست** و
> در جلسه‌های ۷ و ۸ و ۱۱ پسش می‌دهم. آن روز خودم یادآوری می‌کنم.»

این صداقت، **خودش یک درس است**: مهندس خوب گاهی تصمیمی می‌گیرد که سودش بعداً می‌آید.

### ۱.۳ چرا دقیقاً **دو** فایل، نه پنج؟

این نکته به‌اندازه‌ی خودِ تقسیم مهم است، و اغلب فراموش می‌شود. اگر بچه‌ها یاد بگیرند
«فایل زیاد = خوب»، بعداً برای یک تمرین ۵۰ خطی، ۹ فایل می‌سازند و برنامه‌نویسی را رها می‌کنند.

> ## فایل تازه وقتی می‌سازیم که **درد** داشته باشیم — نه از پیش، محض احتیاط.

امروز ما دقیقاً **یک** درد داریم: قواعد و حرف‌زدن قاتیِ همند. پس دقیقاً **یک** تقسیم.
نه پوشه، نه `utils.py`، نه `constants.py`. رشد پروژه در این دوره این‌طور است:

| جلسه | فایل‌ها | دردی که آن فایل را ساخت |
|---|---|---|
| ۳ | `game.py` | — |
| **۴** | `engine.py` + `game.py` | قواعد و نمایش قاتی بودند |
| ۶ | `questions.json` اضافه می‌شود | داده وسط کد بود؛ خواهر کوچکم نمی‌تواند سؤال اضافه کند |
| ۷ | `test_engine.py` اضافه می‌شود | هر بار باید دستی بازی می‌کردیم تا مطمئن شویم چیزی نشکسته |

هر فایل، **جواب یک درد مشخص** است. این جمله را چند بار در دوره تکرار کنید.

### ۱.۴ نکته: بازی مرجعِ دست خودتان چند فایل دارد — نشانش ندهید

نسخه‌ی مرجعی که در جلسه‌ی ۱ دمو دادید پوشه‌بندی دارد (`game/`, `ui/`, `config.py`).
**امروز ساختار آن را به بچه‌ها نشان ندهید.** آن ساختار حاصل رشد است؛ دیدنش قبل از
حس‌کردن دردهایش، هم می‌ترساند و هم همان درسِ «فایل زیاد = خوب» غلط را می‌کارد.
اگر کسی پرسید «مال شما چند فایل داشت؟» بگویید:

> «مال من بزرگ‌تر است چون دردهای بیشتری خورده. مال شما هم آخر دوره بزرگ‌تر می‌شود —
> هر بار به اندازه‌ی یک درد.»

> مغزِ تو نمی‌داند داری فارسی حرف می‌زنی یا انگلیسی — برایش مهم هم نیست.»

آخرین جمله را جدی بگیرید: همان است که در جلسه‌ی ۱۱ اجازه می‌دهد ظاهر عوض شود و موتور نه.

### حرکت ۲ (۲ دقیقه، بدون کامپیوتر) — نمایشِ زنده‌ی قانون

این را حتماً اجرا کنید؛ ارزشش از ده دقیقه توضیح بیشتر است. دو داوطلب:

- **مغز** پشتش به کلاس است، **حق حرف‌زدن ندارد**. فقط کاغذ می‌گیرد و کاغذ پس می‌دهد.
- **دهان** رو به کلاس است، سؤال را بلند می‌خواند، جواب را از کلاس می‌گیرد.

یک راند بازی کنید: دهان روی کاغذ می‌نویسد `A، ۱۲ ثانیه` و به مغز می‌دهد؛ مغز روی کاغذ
می‌نویسد `درست، +۱۳` و پس می‌دهد؛ دهان آن را **تبدیل به جمله** می‌کند: «آفرین علی! ۱۳ امتیاز!»

دو چیز اینجا **بدنی** یاد گرفته می‌شود که با حرف یاد گرفته نمی‌شود:
1. موتور `print` ندارد — چون مغزِ ما امروز اجازه‌ی حرف‌زدن نداشت.
2. 🌱 «برای امتحان‌کردن مغز، لازم نبود کل بازی را بازی کنیم؛ فقط کاغذ دادیم و کاغذ گرفتیم.»
   ← این بذر جلسه‌ی ۷ است. **بگویید و ردش کنید، توضیحش ندهید.**

### حرکت ۳ — سؤالِ تکرارشونده که خودِ درس است

از دقیقه‌ی ۲۵ تا آخر جلسه، هر بار که کسی می‌خواهد چیزی اضافه کند، **قبل از تایپ** بپرسید:

> ## «این تغییر برای **قواعد** است یا برای **نمایش**؟»

و منتظر جواب بمانید. حداقل **پنج بار** در جلسه. جواب، خودش فایل را انتخاب می‌کند.
هدف این است که آخر جلسه، بچه‌ها این سؤال را **از خودشان** بپرسند. ساختار فایل‌ها فقط
نتیجه‌ی این سؤال است؛ اگر سؤال جا بیفتد، ساختار خودش می‌آید.

### حرکت ۴ (دقیقه‌ی ۷۸، ۶۰ ثانیه) — ⭐ مدرکِ نقدی با git

این تنها جایی است که می‌توانید ادعایتان را **امروز ثابت کنید**. بعد از مسابقه، روی
لپ‌تاپ یک تیم (یا خودتان):

```bash
git status
```
یک تغییر کوچکِ فقط-نمایشی بدهید — مثلاً رنگ یک پیام در `game.py` را عوض کنید — و بعد:

```bash
git diff --stat
```

خروجی چیزی شبیه این است:

```
 game.py | 2 +-
 1 file changed, 1 insertion(+), 1 deletion(-)
```

انگشتتان را بگذارید روی `1 file changed` و بگویید:

> «ظاهر بازی عوض شد و **موتور حتی لمس نشد**. git خودش دارد این را به شما می‌گوید.
> اگر همه‌چیز در یک فایل بود، اینجا می‌نوشت هر چیزی که دست‌کاری کردم در همان فایلی است
> که قواعد بازی هم آنجاست.»

چرا این حرکت قوی است: بچه‌ها git را جلسه‌ی ۳ یاد گرفتند، پس این «حرف مربی» نیست —
**ابزار** دارد گزارش می‌دهد. جلسه‌ی ۵ همین را روی GitHub دوباره می‌بینند.

### حرکت ۵ — یک جمله، عیناً، تا آخر دوره

یک شعار داشته باشید و **کلمه‌هایش را عوض نکنید**:

> ## «قواعد در مغز، حرف‌زدن در دهان.»

هر بار که یک `print` در `engine.py` دیدید، خودتان چیزی نگویید — فقط این جمله را بگویید و
منتظر بمانید. تا دقیقه‌ی ۶۰، بچه‌ها آن را برای هم تکرار می‌کنند. تنوع در جمله‌بندی،
این اثر را از بین می‌برد.

### حرکت ۶ — به مخالف جایزه بدهید

یکی حتماً می‌گوید **«یک فایل راحت‌تر بود»**. این بهترین اتفاق جلسه است؛ خفه‌اش نکنید و
بحث را نبرید. اسمش را روی گوشه‌ی تخته بنویسید:

> «حق داری. **امروز** یک فایل راحت‌تر است. این را می‌نویسم به اسم تو، عنوانش هم
> "قرضِ مربی". جلسه‌ی ۷ می‌آیم سراغ تو و پسش می‌دهم.»

و **واقعاً** در جلسه‌ی ۷ به اسم صدایش کنید. دو چیز اینجا آموزش داده می‌شود که هیچ کدشان
در کد نیست: شکاکیت ارزش دارد، و تصمیم مهندسی گاهی سودش را با تأخیر می‌دهد.

### چکِ ۳۰ ثانیه‌ای که به خودشان می‌دهید

تا آخر دوره این را دستشان بدهید تا **بدون شما** بتوانند خودشان را چک کنند:

> **`engine.py` را باز کن و بگرد. اگر حتی یک جمله‌ی فارسی که یک *آدم* بخواند در آن هست،
> جایش غلط است.**

روی ویندوز: `findstr /n "print( input(" engine.py` — باید خالی باشد.

## بخش ۳ — چیزهایی که **نگویید**

این چهار جمله، همه‌شان به نظر بی‌ضرر می‌آیند و هر چهار تا این درس را خراب می‌کنند:

| ❌ نگویید | چرا خراب می‌کند | ✅ جایش |
|---|---|---|
| «چون حرفه‌ای‌ها این‌طور می‌کنند» | استدلالِ اقتدار؛ تقلید کورکورانه یاد می‌دهد | «چون این دو چیز به دو دلیل مختلف عوض می‌شوند» |
| «چون کد مرتب‌تر می‌شود» | مرتبی سلیقه‌ای است — و بچه به‌حق فکر می‌کند *یک* فایل مرتب‌تر از دو فایل است | «چون وقتی امتیاز غلط شد، می‌دانی کدام فایل را باز کنی» |
| «چون فایل بزرگ بد است» | غلط است. معیار اندازه نیست | «معیار اندازه نیست؛ **دلیلِ تغییر** است» |
| «این الگوی معماری MVC / جداسازی دغدغه‌هاست» | اصطلاح، جای فهم را می‌گیرد؛ کلمه را حفظ می‌کنند و ایده را نه | 🧠 مغز / 👄 دهان |

و دو تای دیگر که مخصوص امروز است:

- ❌ **جواب دادن به «چرا کرنومتر در موتور نباشد؟»** — قله‌ی جلسه‌ی ۷ است.
- ❌ **ساختن فایل سوم «برای تمیزی»** — حتی اگر وسوسه شدید. درد سوم هنوز نیامده.

## بخش ۴ — دو سؤال سختی که ممکن است بپرسند

**«اگر موتور بخواهد بگوید جواب غلط بود، چطور؟ آن هم حرف‌زدن نیست؟»**
> «نه. موتور **خبر** را برمی‌گرداند: `"wrong"`. اینکه این خبر بشود "اشتباه بود!" یا
> "نه بابا!" یا رنگ قرمز، کارِ دهان است. موتور *واقعیت* را می‌دهد، *جمله* را نه.»

سؤال درجه‌یکی است؛ تحسینش کنید. (و اگر پرسیدند «پس `ValueError` چه؟» → «آن هم جمله‌سازی
نیست، **اعلام خطر** است. دهان تصمیم می‌گیرد چطور نشانش دهد — جلسه‌ی ۹.»)

**«می‌شود دهان را عوض کنیم و بازی همان بماند؟»**
> «دقیقاً کاری که جلسه‌ی ۱۱ می‌کنیم. و آن روز موتور را **دست هم نمی‌زنیم**.» 🌱
