### ستون سوم برگه: **جنسِ هر داده**

وقتی ستون «چه می‌داند؟» پر شد، برای هر سطر یک سؤال دیگر بپرسید:
**«این یکی چه جنسی است؟ عدد؟ نوشته؟ لیست؟»**

| ویژگی | جنسش | در پایتون |
|---|---|---|
| متن سؤال | نوشته | `str` |
| گزینه‌ها | لیستی از نوشته | `list[str]` |
| امتیاز | عدد صحیح | `int` |
| چند ثانیه طول کشید | عدد اعشاری | `float` |
| درست بود یا نه | بله/خیر | `bool` |
| برنده | یک نام… یا هیچ‌کس | `str | None` |

سطر آخر را جدی بگیرید و بپرسید: **«جنسِ برنده چیست، وقتی مساوی می‌شود؟»**
این سؤال، `None` را از یک «چیز عجیب» به یک **جنسِ داده‌ی معنادار** تبدیل می‌کند.

> «از امروز کنار هر ورودی و خروجی، **جنسش** را هم می‌نویسیم. پایتون مجبورمان نمی‌کند —
> این را برای *آدمی* می‌نویسیم که سه هفته بعد این کد را می‌خواند. که خودت هستی.»

⏱ ۲ دقیقه بیشتر نگیرید. جدول کامل در برگه‌ی طراحی چاپ شده است.

## دقیقه‌ی ۲۳ تا ۲۵ — عادت تازه: خطِ زیر (`_`) یعنی «دست نزن»

**۹۰ ثانیه، و با یک سؤال شروع کنید:**

> «فرض کنید امتیاز من ۵ است و امتیاز تو ۲۰. من یک خط کد می‌نویسم:
> `match.scores["من"] = 1000`. چه شد؟»

می‌خندند و می‌گویند **تقلب**. حالا:

> «امروز جوری می‌نویسیم که این خط **کار نکند**. هر چیزی که مالِ خودِ کلاس است، اسمش
> با `_` شروع می‌شود: `_scores`، `_round`، `_answers`. یعنی «مالِ من است، از بیرون
> دست نزن». به‌جایش یک **پنجره‌ی خواندنی** می‌گذاریم: از بیرون می‌توانی بپرسی
> `match.score_of("علی")`، ولی نمی‌توانی عوضش کنی.»

```
از بیرون:  می‌شود پرسید ✅        نمی‌شود عوض کرد ❌
```

اسمش را هم بگویید و رد شوید: **کپسوله‌سازی**. تعریفِ حفظ‌کردنی ندهید؛ تعریفش همان
جمله‌ی تقلب است.

> **این را همین‌جا بگویید:** «دقیقه‌ی ۵۵ خودم جلوی چشمتان تقلب می‌کنم و می‌بینید
> پایتون چطور جلویم را می‌گیرد.»

🧑‍🏫 **نکته‌ی مربی:** پنجره‌های خواندنی (`@property`) در فایل اسکلت **از قبل نوشته شده‌اند**.
بچه‌ها آن‌ها را تایپ نمی‌کنند — تشریفات است و چیزی یاد نمی‌دهد. فقط باید بدانند
آن بالا چه کاری می‌کنند. همین.

> 📖 **قبل از کلاس، [پیوست الف](#-پیوست-الف--چرا-چند-فایل-شد-راهنمای-کامل-مربی) را بخوانید**
> (انتهای همین فایل): دلیل واقعیِ تقسیم فایل، شش حرکت عملی برای جا انداختنش، و چهار جمله‌ای
> که نباید بگویید. **مهم‌ترین ایده‌ی مهندسیِ کل دوره همین است و تنها ایده‌ای است که
> امروز نمی‌توانید ثابتش کنید** — پس فقط شما می‌توانید بکاریدش.

## دقیقه‌ی ۲۵ تا ۳۲ — کلاس `Question`

این را **کامل با هم تایپ کنند** (اسکلتش را پر می‌کنند) — چون `__init__` و `self` مفهوم تازه‌اند:

```python
class Question:
    def __init__(self, text: str, options: list[str], correct: str) -> None:
        if len(options) != 4:
            raise ValueError("هر سؤال باید دقیقاً ۴ گزینه داشته باشد")
        if correct not in ["A", "B", "C", "D"]:
            raise ValueError("جواب درست باید یکی از A، B، C یا D باشد")

        self._text: str = text
        self._options: list[str] = list(options)   # کپی می‌گیریم، نه خودِ لیستِ بیرون
        self._correct: str = correct

    def is_correct(self, choice: str) -> bool:
        return choice.strip().upper() == self._correct

    def correct_text(self) -> str:
        return self._options["ABCD".index(self._correct)]
```

*(سه `@property` بالای `is_correct` در اسکلت از قبل نوشته شده — تایپش نمی‌کنند.)*

**پنج نکته‌ی گذری:**
- `self` = «خودِ این سؤال». «وقتی صد سؤال داریم، `self` می‌گوید حرف کدامشان است.»
- **`text: str` و `-> bool`** — «جنسِ ورودی و جنسِ خروجی. همان ستون سومِ برگه‌ی طراحی،
  حالا داخل کد.» بپرسید: **«`-> bool` چه قولی به من می‌دهد؟»** → «که جوابش بله/خیر است.»
- **دو `raise` در ابتدای `__init__`** — «کلاس **از خودش محافظت می‌کند**. سؤال با ۳ گزینه
  یا جوابِ درستِ «E» اصلاً ساخته نمی‌شود.» بپرسید: «بهتر است غلط ساخته شود و وسط بازی
  بترکد، یا همان اول ساخته نشود؟»
- **`list(options)` نه `options`** — یک دقیقه رویش بایستید، نکته‌ی نابی است:
  «کپی می‌گیریم. اگر خودِ لیستِ بیرون را نگه می‌داشتیم، هر کسی بیرون آن را عوض می‌کرد،
  گزینه‌های سؤالِ ما هم عوض می‌شد — بی‌اینکه ما بفهمیم.»
- `.strip().upper()` — همان چیزی که جلسه‌ی ۱ نوشتند، حالا **یک‌جا برای همه‌ی سؤال‌ها**.
  بگویید: «قانون درستیِ جواب فقط در یک نقطه از کل برنامه نوشته شده.»

**تست فوری در ترمینال (۱ دقیقه، از دستش ندهید):**

**آن خط آخر را دو بار بزنید.** «سؤال، ساخته شد و دیگر عوض نمی‌شود. پایتون خودش
جلویم را گرفت — نه من، نه شما، نه هیچ‌کس.» *(ترجمه‌ی خطا: «این ویژگی جای نوشتن ندارد».)*

> «موتور را بدون هیچ بازی‌ای امتحان کردیم. **این خودش یک اشاره است به جلسه‌ی ۷.**»

## دقیقه‌ی ۳۲ تا ۴۵ — `Match`: ساختن، شروع راند، ثبت جواب

```python
class Match:
    def __init__(self, player1: str, player2: str, questions: list[Question]) -> None:
        if player1 == player2:
            raise ValueError("نام دو بازیکن نمی‌تواند یکی باشد")
        if len(questions) < ROUNDS:
            raise ValueError(f"برای {ROUNDS} راند، حداقل {ROUNDS} سؤال لازم است")

        self._players: list[str] = [player1, player2]
        self._questions: list[Question] = list(questions)
        self._scores: dict[str, int] = {player1: 0, player2: 0}
        self._round: int = 0                                   # ۰ یعنی هنوز شروع نشده
        self._answers: dict[str, tuple[str, float]] = {}       # نام → (گزینه، ثانیه)

    def start_round(self) -> Question:
        self._round += 1
        self._answers = {}
        return self._questions[self._round - 1]

    def submit(self, player: str, choice: str, elapsed: float) -> None:
        if player not in self._scores:
            raise ValueError(f"بازیکنی به نام {player} در این مسابقه نیست")
        self._answers[player] = (choice, elapsed)

    def is_over(self) -> bool:
        return self._round >= ROUNDS

    def winner(self) -> str | None:
        player1, player2 = self._players
        if self._scores[player1] == self._scores[player2]:
            return None
        if self._scores[player1] > self._scores[player2]:
            return player1
        return player2
```

*(چهار پنجره‌ی خواندنی — `players`، `round`، `score_of`، `answer_of` — در اسکلت
از قبل نوشته شده‌اند. یک بار روی پرده نشانشان بدهید و بگویید «راه ورودِ دهان به مسابقه
همین چهار تاست، نه بیشتر.»)*

**پنج نکته:**
- `raise ValueError(...)` — «موتور اجازه نمی‌دهد مسابقه‌ی بی‌معنا ساخته شود. **فریاد می‌زند.**»
  ⚠️ عمداً در `game.py` مدیریتش نمی‌کنیم — خوراک جلسه‌ی ۹.
- **`dict[str, int]` و `dict[str, tuple[str, float]]`** — این دو را بلند بخوانید:
  «`_scores` یعنی از **نام** به **عدد**. `_answers` یعنی از **نام** به **(گزینه، ثانیه)**.»
  بپرسید: «اگر این را نمی‌نوشتم، سه هفته بعد یادت می‌ماند در `_answers` چه ریخته‌ام؟»
- **همه‌ی ویژگی‌ها `_` دارند** — «موتور از این به بعد **جعبه‌ی بسته** است. حتی `game.py`
  خودمان هم نمی‌تواند داخلش دست ببرد.»
- `self._round - 1` — «راند ۱ یعنی سؤال شماره‌ی صفرِ لیست. یک دقیقه روی همین بایستید،

- `winner()` با جنسِ `str | None` — «یا یک **نام** برمی‌گردد، یا **هیچ‌کس**. جنسش
  همین را می‌گوید، قبل از اینکه کد را بخوانی.»

# ۴۵ تا ۶۰ — `resolve_round`: قلب موتور

این سخت‌ترین ۱۵ دقیقه‌ی جلسه است. **چهار مرحله، روی تخته بنویسید قبل از تایپ:**

```
۱) برای هر بازیکن: درست بود؟ غلط بود؟ دیر شد؟
۲) بین درست‌جواب‌ها، سریع‌ترین را پیدا کن → بونوس
۳) امتیازها را به _scores اضافه کن
۴) نتیجه را برگردان (چاپ نکن!)
```

**قبل از تایپ، ۶۰ ثانیه برای کلاس سوم — `RoundResult`.** بپرسید:

> «نتیجه‌ی هر بازیکن در هر راند، دو تکه دارد: چه شد، و چند امتیاز. این را چطور نگه داریم؟»

معمولاً می‌گویند dict. قبولش کنید و بعد بگویید:

> «می‌شود. ولی این dict **همیشه** دقیقاً همین دو کلید را دارد، نه کم و نه زیاد.
> هر dict که کلیدهایش همیشه ثابت است، در واقع یک **کلاس** است که خودش را قایم کرده.»

```python
class RoundResult:
    def __init__(self, status: str, points: int) -> None:
        self._status: str = status         # "correct" یا "wrong" یا "too_late"
        self._points: int = points

    def add_bonus(self, amount: int) -> None:
        """تنها راهِ مجاز برای عوض‌کردن points"""
        self._points += amount
```

*(دو `@property` — `status` و `points` — در اسکلت آماده است.)*

دو سود این کلاس را نشان بدهید، چون هر دو **دیدنی**‌اند:
- `result.points` به‌جای `result["points"]` — **VS Code خودش پیشنهاد می‌دهد**؛
  با dict نمی‌توانست. بگذارید نقطه را تایپ کنند و لیست بالا آمدنش را ببینند.
- `results["علی"]["pionts"]` یک **غلط املایی** بود که فقط وسط بازی می‌ترکید.
  `result.pionts` را همین حالا امتحان کنند: ویرایشگر **قبل از اجرا** زیرش خط می‌کشد.

```python
    def resolve_round(self) -> dict[str, RoundResult]:
        question = self._questions[self._round - 1]
        results: dict[str, RoundResult] = {}
        correct_players: list[str] = []

        # ۱) درست بود، غلط بود، یا دیر؟
        for player in self._players:
            choice, elapsed = self._answers[player]

            if elapsed > TIME_LIMIT:
                results[player] = RoundResult("too_late", 0)
            elif question.is_correct(choice):
                results[player] = RoundResult("correct", POINTS)
                correct_players.append(player)
            else:
                results[player] = RoundResult("wrong", 0)

        # ۲) بونوس سرعت: بین درست‌جواب‌ها، سریع‌ترین
        if correct_players:
            fastest = correct_players[0]
            for player in correct_players:
                if self._answers[player][1] < self._answers[fastest][1]:
                    fastest = player
            results[fastest].add_bonus(SPEED_BONUS)

        # ۳) امتیازها را جمع کن  ← اینجا، *داخل* موتور، مجاز است
        for player in self._players:
            self._scores[player] += results[player].points

        return results
```

**شش نکته‌ی مهم:**

- **ترتیب `if` مهم است.** بپرسید: «اگر کسی جواب **درست** بدهد ولی در ۳۵ ثانیه، چه می‌شود؟»
  → صفر. «چون اول مهلت را چک می‌کنیم.» این تصمیم را بلند بگویید.
- **`if correct_players:`** — «اگر هر دو غلط بدهند، بونوس به کسی نمی‌رسد.»
  بپرسید: «اگر این `if` نبود چه می‌شد؟» → خطا، چون `correct_players[0]` وجود ندارد.
- **الگوی پیدا کردن کمینه** — «اولی را بردار، بعد هر کس بهتر بود جایش را بگیر.»
  این الگو را بچه‌ها تا آخر عمر لازم دارند.
- **`results[fastest].add_bonus(SPEED_BONUS)`** — «قبلاً می‌نوشتیم `+= ۳` روی یک dict.
  حالا از خودِ نتیجه **می‌خواهیم** که بونوس بگیرد. اسم کار، در خودِ کد نوشته شده.»
- **`self._scores[player] += ...` اینجا مجاز است** — این را بپرسید، سؤال طلایی است:
  **«مگر نگفتیم `_scores` دست‌نخوردنی است؟ پس چرا اینجا دست زدیم؟»**
  → «چون **اینجا داخلِ خودِ کلاس است**. `_` یعنی «از بیرون دست نزن»، نه «هیچ‌کس دست نزند».
  خودِ موتور صاحبِ امتیازهاست؛ فقط بیرونی‌ها مهمانند.»
- **`return results` و نه `print`** — «موتور **نتیجه** می‌دهد؛ جمله‌سازی و رنگ کار دهان است.»
  اینجا به قانون تخته اشاره کنید.

# سؤال‌هایی که بچه‌ها می‌پرسند

**«چرا دو فایل؟ یک فایل راحت‌تر بود.»** ← **بهترین سؤال جلسه. بحث را نبرید.**
> «حق داری، **امروز** یک فایل راحت‌تر است. اسمت را می‌نویسم روی تخته به عنوان "قرضِ مربی"،
> و جلسه‌ی ۷ می‌آیم سراغ تو و پسش می‌دهم.»

جواب کوتاهِ نقدی که *امروز* قابل نشان‌دادن است: «وقتی امتیاز غلط شد، می‌دانی کدام فایل را
باز کنی.» بقیه‌ی فایده‌ها وعده‌ی جلسه‌های ۷، ۸ و ۱۱ است. → **[پیوست الف](#-پیوست-الف--چرا-چند-فایل-شد-راهنمای-کامل-مربی)، بخش ۱.۲ و حرکت ۶.**

**«`self` یعنی چی؟»**
> «یعنی *خودِ این یکی*. صد سؤال داریم؛ `self.text` می‌گوید متنِ **همین** سؤال.»

## بخش ۱ — دلیل واقعی، برای خودتان

### ۱.۱ دلیلِ درست: سرعتِ تغییر، نه مرتب‌بودن

بزرگ‌ترین اشتباه در آموزش این مبحث این است که به‌عنوان «نظم و مرتبی» معرفی شود.
دلیل واقعی این است:

> ## تکه‌های یک برنامه با **سرعت‌های مختلف** و به **دلیل‌های مختلف** عوض می‌شوند.

- قواعد بازی وقتی عوض می‌شوند که بخواهید **بازی** فرق کند (بونوس ۵ شود، سرقت اضافه شود).
- نمایش وقتی عوض می‌شود که بخواهید **قشنگ‌تر** شود (رنگ، نوار، جدول، بعداً پنجره‌ی گرافیکی).

این دو هیچ ربطی به هم ندارند، در **زمان‌های مختلف** عوض می‌شوند، و اغلب توسط
**آدم‌های مختلف**. وقتی در یک فایل باشند، هر دست‌کاری در یکی، ریسکِ خرابیِ آن یکی است.

پس معیار تقسیم، **اندازه نیست**. یک فایل ۴۰ خطی می‌تواند غلط تقسیم شده باشد و یک فایل
۳۰۰ خطی درست باشد. معیار این است:

> ## «چیزهایی که **به یک دلیل** عوض می‌شوند کنار هم؛ چیزهایی که به **دلیل‌های مختلف** عوض می‌شوند، جدا.»

این جمله دقیقاً همان چیزی است که در دنیای حرفه‌ای «اصل مسئولیت واحد» نامیده می‌شود —
ولی این نسخه‌ی درستش است، نه نسخه‌ی «هر فایل کوچک باشد».

### ۱.۲ چهار سود این تقسیم — و اینکه هر کدام کِی نقد می‌شود

این جدول قلب پیوست است. بخوانید و **باور کنید**، چون بچه‌ها امروز فقط سود چهارم را می‌بینند:

| سود | چه می‌گوید | کِی برای بچه‌ها **ثابت** می‌شود |
|---|---|---|
| ۱. **قابل آزمایش‌شدن** | موتوری که `print`/`input` ندارد را می‌شود هزار بار در یک ثانیه اجرا کرد | **جلسه‌ی ۷ (pytest) — قله‌ی دوره** |
| ۲. **تعویض ظاهر** | مغز ثابت، صورت عوض‌شدنی؛ همان بازی با ظاهر تازه | جلسه‌ی ۱۱ (صیقل) |
| ۳. **کار دونفره** | دو نفر در یک فایل به هم می‌خورند؛ در دو فایل نه | جلسه‌ی ۸ (branch و conflict) |
| ۴. **پیدا کردن باگ** | «امتیاز غلط است» → یعنی `engine.py`. «شکل غلط است» → یعنی `game.py` | **همین امروز، دقیقه‌ی ۷۰** |

**نتیجه‌ی آموزشی مهم:** سه سود از چهار سود، **وعده‌ی آینده** است. یعنی امروز شما
نمی‌توانید این تصمیم را با استدلال ببرید — و **نباید هم تلاش کنید**. راهش این است که
سود چهارم را امروز نقداً نشان دهید، و سه سود دیگر را صادقانه به‌عنوان قرض معرفی کنید:

> «امروز فقط یکی از چهار فایده را می‌بینی. سه فایده‌ی دیگر **قرض من به شماست** و
> در جلسه‌های ۷ و ۸ و ۱۱ پسش می‌دهم. آن روز خودم یادآوری می‌کنم.»

این صداقت، **خودش یک درس است**: مهندس خوب گاهی تصمیمی می‌گیرد که سودش بعداً می‌آید.

### ۱.۳ چرا دقیقاً **دو** فایل، نه پنج؟

این نکته به‌اندازه‌ی خودِ تقسیم مهم است، و اغلب فراموش می‌شود. اگر بچه‌ها یاد بگیرند
«فایل زیاد = خوب»، بعداً برای یک تمرین ۵۰ خطی، ۹ فایل می‌سازند و برنامه‌نویسی را رها می‌کنند.

> ## فایل تازه وقتی می‌سازیم که **درد** داشته باشیم — نه از پیش، محض احتیاط.

امروز ما دقیقاً **یک** درد داریم: قواعد و حرف‌زدن قاتیِ همند. پس دقیقاً **یک** تقسیم.
نه پوشه، نه `utils.py`، نه `constants.py`. رشد پروژه در این دوره این‌طور است:

| جلسه | فایل‌ها | دردی که آن فایل را ساخت |
|---|---|---|
| ۳ | `game.py` | — |
| **۴** | `engine.py` + `game.py` | قواعد و نمایش قاتی بودند |
| ۶ | `questions.json` اضافه می‌شود | داده وسط کد بود؛ خواهر کوچکم نمی‌تواند سؤال اضافه کند |
| ۷ | `test_engine.py` اضافه می‌شود | هر بار باید دستی بازی می‌کردیم تا مطمئن شویم چیزی نشکسته |

هر فایل، **جواب یک درد مشخص** است. این جمله را چند بار در دوره تکرار کنید.

### ۱.۴ نکته: بازی مرجعِ دست خودتان چند فایل دارد — نشانش ندهید

نسخه‌ی مرجعی که در جلسه‌ی ۱ دمو دادید پوشه‌بندی دارد (`game/`, `ui/`, `config.py`).
**امروز ساختار آن را به بچه‌ها نشان ندهید.** آن ساختار حاصل رشد است؛ دیدنش قبل از
حس‌کردن دردهایش، هم می‌ترساند و هم همان درسِ «فایل زیاد = خوب» غلط را می‌کارد.
اگر کسی پرسید «مال شما چند فایل داشت؟» بگویید:

> «مال من بزرگ‌تر است چون دردهای بیشتری خورده. مال شما هم آخر دوره بزرگ‌تر می‌شود —
> هر بار به اندازه‌ی یک درد.»

## بخش ۲ — شش حرکت عملی سر کلاس

### حرکت ۰ (دقیقه‌ی ۱۰) — اول درد، بعد دارو

**هرگز با راه‌حل شروع نکنید.** قبل از هر حرفی از تقسیم فایل، فایل `game.py` جلسه‌ی ۳ را
روی پروژکتور باز کنید و دو سؤال بپرسید — و **بگذارید واقعاً بگردند**:

> ۱) «می‌خواهم امتیاز جواب درست ۲۰ شود. کدام خط؟»
> ۲) «می‌خواهم رنگ‌ها را عوض کنم. کدام خط؟»

بعد انگشتتان را روی صفحه بکشید و بگویید:
> «ببینید. خطِ قاعده، خطِ رنگ، خطِ قاعده، خطِ رنگ… **قاتی‌اند.** امروز از هم جدایشان می‌کنیم.»

۹۰ ثانیه وقت می‌گیرد و کل جلسه را می‌سازد. اگر این حرکت را رد کنید، تقسیم فایل تا آخر
جلسه «کارِ اضافه‌ای که مربی خواست» می‌ماند.

### حرکت ۱ — استعاره‌ی بدن، نه استعاره‌ی نرم‌افزاری

برای این سن، 🧠 **مغز** و 👄 **دهان** از «لایه» و «ماژول» و «معماری» بی‌نهایت بهتر کار می‌کند.
استعاره را کامل بسازید:

> «مغز تصمیم می‌گیرد و **حرف نمی‌زند**. دهان حرف می‌زند و **تصمیم نمی‌گیرد**.
> مغزِ تو نمی‌داند داری فارسی حرف می‌زنی یا انگلیسی — برایش مهم هم نیست.»

آخرین جمله را جدی بگیرید: همان است که در جلسه‌ی ۱۱ اجازه می‌دهد ظاهر عوض شود و موتور نه.

### حرکت ۲ (۲ دقیقه، بدون کامپیوتر) — نمایشِ زنده‌ی قانون

این را حتماً اجرا کنید؛ ارزشش از ده دقیقه توضیح بیشتر است. دو داوطلب:

- **مغز** پشتش به کلاس است، **حق حرف‌زدن ندارد**. فقط کاغذ می‌گیرد و کاغذ پس می‌دهد.
- **دهان** رو به کلاس است، سؤال را بلند می‌خواند، جواب را از کلاس می‌گیرد.

یک راند بازی کنید: دهان روی کاغذ می‌نویسد `A، ۱۲ ثانیه` و به مغز می‌دهد؛ مغز روی کاغذ
می‌نویسد `درست، +۱۳` و پس می‌دهد؛ دهان آن را **تبدیل به جمله** می‌کند: «آفرین علی! ۱۳ امتیاز!»

دو چیز اینجا **بدنی** یاد گرفته می‌شود که با حرف یاد گرفته نمی‌شود:
1. موتور `print` ندارد — چون مغزِ ما امروز اجازه‌ی حرف‌زدن نداشت.
2. 🌱 «برای امتحان‌کردن مغز، لازم نبود کل بازی را بازی کنیم؛ فقط کاغذ دادیم و کاغذ گرفتیم.»
   ← این بذر جلسه‌ی ۷ است. **بگویید و ردش کنید، توضیحش ندهید.**

### حرکت ۳ — سؤالِ تکرارشونده که خودِ درس است

از دقیقه‌ی ۲۵ تا آخر جلسه، هر بار که کسی می‌خواهد چیزی اضافه کند، **قبل از تایپ** بپرسید:

> ## «این تغییر برای **قواعد** است یا برای **نمایش**؟»

و منتظر جواب بمانید. حداقل **پنج بار** در جلسه. جواب، خودش فایل را انتخاب می‌کند.
هدف این است که آخر جلسه، بچه‌ها این سؤال را **از خودشان** بپرسند. ساختار فایل‌ها فقط
نتیجه‌ی این سؤال است؛ اگر سؤال جا بیفتد، ساختار خودش می‌آید.

### حرکت ۴ (دقیقه‌ی ۷۸، ۶۰ ثانیه) — ⭐ مدرکِ نقدی با git

این تنها جایی است که می‌توانید ادعایتان را **امروز ثابت کنید**. بعد از مسابقه، روی
لپ‌تاپ یک تیم (یا خودتان):

```bash
git status
```
یک تغییر کوچکِ فقط-نمایشی بدهید — مثلاً رنگ یک پیام در `game.py` را عوض کنید — و بعد:

```bash
git diff --stat
```

خروجی چیزی شبیه این است:

```
 game.py | 2 +-
 1 file changed, 1 insertion(+), 1 deletion(-)
```

انگشتتان را بگذارید روی `1 file changed` و بگویید:

> «ظاهر بازی عوض شد و **موتور حتی لمس نشد**. git خودش دارد این را به شما می‌گوید.
> اگر همه‌چیز در یک فایل بود، اینجا می‌نوشت هر چیزی که دست‌کاری کردم در همان فایلی است
> که قواعد بازی هم آنجاست.»

چرا این حرکت قوی است: بچه‌ها git را جلسه‌ی ۳ یاد گرفتند، پس این «حرف مربی» نیست —
**ابزار** دارد گزارش می‌دهد. جلسه‌ی ۵ همین را روی GitHub دوباره می‌بینند.

### حرکت ۵ — یک جمله، عیناً، تا آخر دوره

یک شعار داشته باشید و **کلمه‌هایش را عوض نکنید**:

> ## «قواعد در مغز، حرف‌زدن در دهان.»

هر بار که یک `print` در `engine.py` دیدید، خودتان چیزی نگویید — فقط این جمله را بگویید و
منتظر بمانید. تا دقیقه‌ی ۶۰، بچه‌ها آن را برای هم تکرار می‌کنند. تنوع در جمله‌بندی،
این اثر را از بین می‌برد.

### حرکت ۶ — به مخالف جایزه بدهید

یکی حتماً می‌گوید **«یک فایل راحت‌تر بود»**. این بهترین اتفاق جلسه است؛ خفه‌اش نکنید و
بحث را نبرید. اسمش را روی گوشه‌ی تخته بنویسید:

> «حق داری. **امروز** یک فایل راحت‌تر است. این را می‌نویسم به اسم تو، عنوانش هم
> "قرضِ مربی". جلسه‌ی ۷ می‌آیم سراغ تو و پسش می‌دهم.»

و **واقعاً** در جلسه‌ی ۷ به اسم صدایش کنید. دو چیز اینجا آموزش داده می‌شود که هیچ کدشان
در کد نیست: شکاکیت ارزش دارد، و تصمیم مهندسی گاهی سودش را با تأخیر می‌دهد.

### چکِ ۳۰ ثانیه‌ای که به خودشان می‌دهید

## بخش ۳ — چیزهایی که **نگویید**

این چهار جمله، همه‌شان به نظر بی‌ضرر می‌آیند و هر چهار تا این درس را خراب می‌کنند:

| ❌ نگویید | چرا خراب می‌کند | ✅ جایش |
|---|---|---|
| «چون حرفه‌ای‌ها این‌طور می‌کنند» | استدلالِ اقتدار؛ تقلید کورکورانه یاد می‌دهد | «چون این دو چیز به دو دلیل مختلف عوض می‌شوند» |
| «چون کد مرتب‌تر می‌شود» | مرتبی سلیقه‌ای است — و بچه به‌حق فکر می‌کند *یک* فایل مرتب‌تر از دو فایل است | «چون وقتی امتیاز غلط شد، می‌دانی کدام فایل را باز کنی» |
| «چون فایل بزرگ بد است» | غلط است. معیار اندازه نیست | «معیار اندازه نیست؛ **دلیلِ تغییر** است» |
| «این الگوی معماری MVC / جداسازی دغدغه‌هاست» | اصطلاح، جای فهم را می‌گیرد؛ کلمه را حفظ می‌کنند و ایده را نه | 🧠 مغز / 👄 دهان |

و دو تای دیگر که مخصوص امروز است:

- ❌ **جواب دادن به «چرا کرنومتر در موتور نباشد؟»** — قله‌ی جلسه‌ی ۷ است.
- ❌ **ساختن فایل سوم «برای تمیزی»** — حتی اگر وسوسه شدید. درد سوم هنوز نیامده.
